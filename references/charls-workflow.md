# CHARLS 变量定义标准流程

版本日期：2026-07-27

适用范围：通过 bookapp 为 CHARLS 定义分析变量，并产出 `db_*.xlsx`、`codebook_*.xlsx`、`analysis_db_*.xlsx`、`analysis_codebook_*.xlsx`。

通用代码与用户材料规则见：`<SKILL_ROOT>\references\user-material-rules.md`。本流程中的 R 代码、QA、HTML 和笔记必须遵守该通用规范。

正式源说明：启用本 Skill 后，本文件的唯一正式位置是 `<SKILL_ROOT>\references\charls-workflow.md`。工作区中的同名旧文件不得作为规则依据。

## 0. 任务入口

用户可以只说一句短需求，例如：

```text
大脑，我定义 CHARLS 的某个主题变量
```

大脑先补齐任务卡，不直接写代码：

- 变量主题：用用户需求转写为一个清晰主题名。
- 正式目录：`<DBCODEBOOK_HOME>\演示\定义\CHARLS_变量名`
- bookapp 数据入口：`http://localhost:8000/`
- 是否必须从目录入口核对：默认是。目录面板中的文字筛选只用于定位目录，不等于普通检索。
- 参考代码：优先沿用用户已确认的项目 R 风格；具体历史参考见 `CHARLS数据库profile.md`。
- 交付物：4 个 xlsx、R 脚本、QA 文本、网页详情 html、完整笔记 md、运行日志、bookapp 原始下载包与 raw 文件。README 只有在用户明确需要目录说明时才生成。

### 0.1 大脑调度边界

CHARLS 定义任务中，大脑是总控，不是默认执行工位。

- 大脑负责确认需求、变量口径、命名规则、编码规则、用户版语言风格、验收标准和派发单。
- 大脑默认不直接修改正式成果目录，不直接改 `define_charls_xxx.R`，不直接重跑 R，不直接刷新 xlsx / QA / HTML / 笔记。
- 用户提出返修或调整时，大脑先把需求翻译成执行线程返修单，写清楚“要改什么、不能改什么、是否允许重跑、是否允许重新下载”。
- 只有用户明确要求“大脑亲自执行/直接改”，或任务本身只是协议、流程、模板、风格规则沉淀时，大脑才在本线程直接动手。
- 涉及正式变量成果的修改，默认交给固定定义执行线程。执行线程同时负责生成与常规验证；机器闸门通过后直接完成并入账。独立验收只用于机器证据冲突、未决研究问题、公共核心机制影响无法由回归界定，或用户/大脑明确要求的异常情况。

## 1. 项目目录规则

正式成果必须放项目目录，不放 Codex 临时线程目录。

固定执行工位：

```text
<DBCODEBOOK_HOME>\演示\定义\_执行线程\
```

这个目录是变量定义任务的长期执行工位，用于保存任务卡、过程日志、handoff、返工说明和执行复盘。它不是正式成果目录，也不是大脑目录。

默认规则：

- 大脑线程制定任务卡、确认边界、派发和复核。
- 固定“定义执行线程”负责 bookapp 操作、raw 包、R 定义、QA、HTML 和笔记生成。
- 固定“定义执行线程”完成正式成果后，必须完成 runner、固定自检、必要回归或复算和过程证据。机器证据完整且一致时直接回大脑并入账。
- 独立验收任务不是常规工位，只读核验异常入口对应的未决事项，不重复执行任务已完成的文件、日志、目录、工作簿和用户材料检查。
- 涉及研究口径且当前规则或用户裁决不足时，执行线程直接回大脑裁决；不得先启动验收线程代替裁决。
- 固定“定义执行线程”必须创建在已保存项目 `<DBCODEBOOK_HOME>\演示` 中，线程运行根目录应为 `<DBCODEBOOK_HOME>\演示`；不能使用 projectless 临时线程来承担长期定义任务。
- 不为每个变量默认新建一个一次性执行线程；除非任务需要并行探索或用户明确要求。
- 每个任务可在 `_执行线程` 下建立过程子目录，例如 `<DBCODEBOOK_HOME>\演示\定义\_执行线程\CHARLS\{主题编号}_{主题名}\`。
- 正式成果仍放各自 `<DBCODEBOOK_HOME>\演示\定义\CHARLS_xxx\`。

推荐结构：


## 1.1 执行线程环境对齐闸门

固定“定义执行线程”不是大脑线程、当前线程或 RStudio 会话的延续。线程之间只共享文件系统和本机服务，不继承：

- 已加载的 R 包。
- `.libPaths()`。
- RStudio/命令行 R 会话状态。
- 环境变量。
- 浏览器工具 runtime。
- 临时缓存。
- 当前工作目录。

因此，当前线程或 RStudio 能运行，不代表固定执行线程能运行。每次定义任务在正式运行 R 脚本前，必须先做一次轻量环境预检，并把结果写入任务卡或运行日志：

- 当前线程 ID 与工作根目录。
- 正式成果目录。
- 实际调用的 R/Rscript 路径。
- `getwd()`。
- `.libPaths()`。
- `devtools`、`openxlsx`、`dplyr`、`tidyr`、`dbCodeBookr` 是否在当前 R 环境可用。
- 脚本运行方式：优先以正式成果目录为工作目录运行，脚本内部使用相对路径读取 `raw_data.csv` 和 `raw_codebook.csv`。

判定规则：

- 环境预检只解释“为什么执行线程可能跑不通同一份正式 R 脚本”，不能替代正式脚本运行。
- 正式 `define_charls_xxx.R` 是唯一可运行对象。执行线程验证时，必须在正式成果目录中直接从头到尾运行这份脚本，并保存完整运行日志。
- 不要用临时 R 片段、环境探针、安装尝试、路径绕行或重写版脚本替代正式脚本运行。
- 如果 R 包、库路径、工作目录或 Rscript 与用户可运行环境不一致，先报告“执行线程环境未对齐”。这不是自动等于 R 代码错误。
- 不要为了让执行线程跑通而临时改写包加载块、追加安装流程、创建用户库、复制包库或换路径绕行。
- 包安装、R 库配置、`dbCodeBookr` 安装更新属于一次性环境准备任务，必须由用户明确同意后单独处理；它不是变量定义流程的一部分。
- 参考用户已确认的既有 R 脚本是为了对齐定义代码风格；若正式脚本本身需要调整，必须基于定义逻辑或用户代码习惯调整，而不是基于执行线程的临时环境问题调整。具体历史参考见 `CHARLS数据库profile.md`。
## 2. bookapp 是事实入口

变量定义任务必须通过浏览器在 bookapp 页面完成真实操作。

硬闸门：

- 没有在 `http://localhost:8000/` 上完成变量检索、详情理解、变量选择、预览、下载，就不能写正式 R 定义。

## 3. 变量检索顺序

优先从左侧目录面板进入相关目录，不直接全局猜变量名。目录面板中的文字筛选只过滤目录名称，不等于普通检索。

推荐顺序：

1. 在左侧目录面板定位最贴近主题的目录节点，例如 `Core data > Health behaviours > Smoking`；需要时可输入文字筛选目录名称。
2. 进入目录节点并查看变量表。
3. 如果目录内容不足以覆盖主题，或需要发现跨目录候选，再执行普通检索；如实记录普通检索关键词和结果。
4. 逐个打开官方问卷详情，确认：
   - 变量名
   - 年份
   - 问题文本
   - 取值标签
   - 跳转逻辑
   - 同名变量跨年份含义是否变化

检索不是只保存最后找到的变量清单。自首次目录浏览起，必须按实际发生顺序同步记录每一步：

- 本步进入的目录或执行的普通检索词；
- 页面实际出现的内容、记录数或值得继续核对的候选；
- 为什么继续打开某个详情、转向另一个目录或增加新的检索词；
- 候选变量最终是纳入、排除还是暂缓，以及作出该选择的具体理由。

记录必须在探索过程中形成，不能等正式变量已经确定后，再根据变量名或最终结果反编一条看似完整的发现路径。最终文案与既有句子是否相同不重要；约束的是事实来源和生成过程。

跨周期主题、量表、认知测验和可能分布在多个调查模块的主题，在目录浏览后必须再用研究概念及常见同义词完成一次普通检索，用于发现其它目录或调查项目中的同类题项。目录面板筛选与普通检索必须分开记录；不能根据既有主题、问卷题号或文件名猜测候选 raw。

不能只看 Easy label。Easy label 可能跨年份漂移：同名或近似标签在不同年份可能对应不同题干、不同路径或不同研究对象。必须逐年点官方问卷详情核验。具体已踩坑变量见 `CHARLS数据库profile.md`。

### 3.1 针对性文献调研与候选闸门

完成 dbCodeBook 目录/普通检索、官方问卷详情核对并形成初步候选后，在变量选择与下载之前进行针对性文献调研。文献调研用于比较已有研究如何界定和构造同一研究概念，不用于替代官方问卷详情、raw 标签或实际数据结构。

证据优先级固定为：

1. 官方问卷详情、实际 raw 取值与 `raw_codebook`。
2. CHARLS 官方用户指南、技术文档、问卷材料，以及可定位构造过程的 Harmonized CHARLS 技术代码本。
3. 原始量表或方法文献、正式指南、共识文件、法律政策和主管机构文件。
4. 在研究设计、变量构造和报告完整性上可靠，且明确给出可复核 CHARLS 题项、raw、公式或计分的同行评议研究。
5. 一般应用研究和研究惯例。

执行要求：

- 所有新定义至少完成一次与本主题直接相关的定向检索；简单单题可简要确认是否存在不同的常见定义。
- 量表、认知测验、总分、指数、复合变量，以及存在多种常见构造、跨周期项目变化或计分歧义的主题，必须进行实质文献调研。
- “已在同行评议期刊发表”只说明来源经过正式发表流程，不等于权威定义。必须同时判断来源与本主题的直接性、期刊与栏目质量、研究设计、变量构造是否完整、题项/周期/公式是否可复核，以及结论是否超出原文证据。大型综合期刊、专题刊或质量波动较大的期刊文章不得仅凭期刊名升级为主要依据。
- 一般应用研究只能说明“已有研究曾这样使用”，不能替官方题目、原始量表、技术代码本或方法文献为定义背书。官方材料已经足以确定题义和构造时，不为增加引用数量而补普通应用论文。
- 正式笔记中的引用优先保留第 1–3 级来源；第 4 级仅在其直接提供本主题不可替代的构造证据时保留。第 5 级默认只进入过程对照，不进入正式笔记。
- 文献调研应记录：文献或官方材料、使用周期/样本、研究概念、纳入项目或 raw（如有）、公式或计分、取值范围、缺失/完整性处理，以及与本轮候选的相同点和差异。
- 每篇实际采用的文献或官方材料必须在过程目录保留可独立阅读的 Markdown 证据正文，不能只在汇总表中写“支持本定义”“定义一致”等结论。正文至少逐项写明：可定位的正式来源、原文所用周期/样本、原文怎样定义研究概念、纳入哪些题项或 raw、具体公式/计分/反向计分、取值范围、完整性与缺失处理，以及它实际支持本轮候选的哪一部分。
- 文献明确给出定义句、题项清单、公式或计分时，Markdown 中保留足以复核构造的具体内容；公式、变量名和编码使用代码块、行内代码或公式块呈现，不得压缩成笼统转述。可作忠实中文说明，但必须与原文内容分开标明，不能把本轮解释伪装成文献原话。
- 文献未报告 raw、计分或缺失细节时，明确记为“未报告”，不得根据研究结果或上下文反推。
- 每一项证据必须区分“来源明确陈述”“根据官方题目/raw 可直接核实”“本轮拟采用方案”。来源没有明确说明的部分不得由执行任务自行补定义；若该缺口会影响变量含义、公式、计分、跨周期可比性或缺失处理，必须进入待裁决问题并停在候选闸门。
- 文献定义与官方问卷、实际 raw 或不同文献之间不一致时，形成候选方案并回大脑/用户裁决；不得自行选取最常见方案。
- 文献证据只进入过程证据和候选包。只有会改变变量含义、可比性或解释边界的结论，才按用户材料公共规则转写到摘要、Criteria 或注意点。
- raw 名称、题义、取值与施测结构必须来自 dbCodeBook 详情、官方材料或实际数据；文献只用于比较定义和解释可比性。凡涉及题目变化、施测方式变化或跨周期可比性的结论，必须在候选包中写明依据，不能从变量名或研究上下文自行推演。

候选包至少包含：

- 逐周期候选 raw、题义、取值、数据结构和纳入/排除理由；每组 raw 同时记录其发现入口、完整目录路径或普通检索词及可定位的详情依据。无法说明发现来源的变量不得进入正式下载。
- 文献定义对照表及可定位的来源。
- 推荐的定义变量、计分方案、完整性规则和推荐理由。
- 仍需裁决的问题。

候选包形成后再进入变量选择。存在未裁决的研究口径时，必须停在候选闸门；不得下载 raw、编写正式 R 或生成正式成果。

### 3.1.1 023 起的源头检索硬闸门

001–022 已由用户完成核对，作为历史接受边界，不因本节追加回溯。自 023 起保留源头记录；本规则更新后新开主题使用 schema v2，并在首次网页检索时同步填写 `definition_search_record.json`，结构以 `<SKILL_ROOT>\assets\retrieval-record-template.json` 为准。已有 schema v1 记录不回填虚构的探索历史。

- `exploration_log` 按顺序记录真实发生的网页操作及当时判断：实际进入的目录、实际执行的普通检索词、页面观察、下一步决定和理由。每一步先记录，再继续探索。
- `candidate_decisions` 记录候选取舍：候选对应什么研究概念、最终纳入或排除哪些 raw、为什么这样选择，以及依据哪些探索步骤。
- `source_groups` 只汇总最终来源组，并指回形成该组的探索步骤；它不能替代探索日志。
- 目录和检索词必须在发现变量时记录，禁止在正式定义阶段根据主题、变量名、文件名或后期结果反推。
- 每个正式 raw 必须归入一个已记录的来源组，并能在候选取舍中找到纳入理由。
- 如果源头记录晚于候选选择或正式 R 才建立，必须标记为回溯核对；它只能证明当前来源可复现，不能冒充最初探索过程。
- 周期断层、同名不同义、题义变化、公式不完整、来源冲突、命名不清或其它逻辑漏洞一经发现，立即停止并向用户汇报其事实、影响和待裁决项。问题未报告、未裁决或未写回记录时，不得继续。
- `run_r_definition.ps1` 对编号 023 及之后的 CHARLS 主题强制执行源头记录检查。schema v2 还必须通过探索步骤、候选取舍和最终 raw 对应检查；记录缺失、raw 未覆盖、正式命名未批准或逻辑问题未解决时，正式 R 拒绝运行。

### 3.1.2 主题独立性与可研究性检查

新主题在分配正式编号、创建正式目录和生成正式成果前，必须完成以下检查：

1. **既有成果查重**：对照已有分析变量的研究含义、原始来源、构造逻辑和实际取值。逐值相同或仅更换名称的变量，直接引用已有主题，不重复定义。候选阶段尚不能逐值比较时，先核对来源与构造；发现疑似重复后，只能在过程目录完成必要的数据对照，不得先生成正式主题。
2. **独立主题判断**：仅对已有变量进行比例、合计、二分类等直接派生时，原则上并入原主题。只有形成独立研究概念、独立解释边界或明确需要单独使用时，才候选为新主题。
3. **按周期评估样本**：分别报告每个可选基线年份的独立受访者有效人数，并注明题目适用对象、筛选条件和跳转路径。不得用全部人次、全部波次合并后的行数或占比判断研究价值。
4. **纵向可用性**：计划纵向使用时，再按个人 ID 报告各候选基线进入后续波次的人数；已有明确结局时，同时评估结局有效人数或事件数。不存在统一人数阈值，必须结合具体研究设计判断。
5. **候选结论**：检查完成后只形成 `NEW`、`MERGE`、`REUSE` 或 `DEFER` 四类结论。`NEW` 表示形成独立新主题；`MERGE` 表示并入已有主题；`REUSE` 表示直接复用已有变量；`DEFER` 表示当前证据、样本或研究设计不足，暂缓定义。

候选工作标识不等于正式主题编号。只有结论为 `NEW`，并且研究口径已经裁决时，才分配正式编号并创建正式主题目录；`MERGE`、`REUSE` 和 `DEFER` 不占用新主题编号。

### 3.2 周期完整性回查

形成初步候选后，先按预期调查周期列出每个研究概念的来源覆盖。若某项来源在前后周期存在、却在中间周期缺失，视为“周期断层”，必须暂停变量下载和正式定义，并回到 dbCodeBook 普通检索、完整目录及官方问卷/代码本核查。

核查后只允许形成三类结论：

- `QUESTION_NOT_ASKED`：该周期确实没有对应题目。
- `MEANING_CHANGED`：存在相关题目，但题义、对象或参考期已经改变，不能直接并入。
- `SOURCE_OMITTED`：对应来源实际存在，只是候选检索或选择时遗漏；必须补齐来源后重新预览和下载。

周期两端自然缺少题目不自动视为错误，但仍需说明覆盖起止。正式生成后再次按周期检查定义变量覆盖；结果与候选覆盖不一致时，不得以“该年未定义”直接收口，必须先回查来源。

## 4. 变量选择与下载

选择变量前必须记录选择依据：

- 直接定义变量：当轮核心问题。
- 预载变量：上一轮或上一次访问信息，只在明确规则下补充。
- 辅助变量：只用于路由或 QA，不一定进入最终分析变量。

下载前必须预览：

- 变量数是否符合预期。
- 行数是否符合预期。
- 列名是否包含 `ID`、`id`、`year` 和所选变量。

正式目录必须保留：

- `bookapp_download.zip`
- `raw_data.csv`
- `raw_codebook.csv`

### 4.1 下载落盘分流处理

bookapp 生成下载记录，不等于文件已经落到本机；下载后必须做三层确认：

1. bookapp 弹窗预览成功，变量数、行数、列名符合预期。
2. localhost 场景优先以 `recover_bookapp_export.py --latest` 的 QA 文本确认本次下载记录和匹配 transaction；仅 `--latest` 失败或无法确认本次记录时，才进入个人中心“下载记录”人工确认 transaction id，并记录回退原因。
3. 正式项目目录实际存在本次下载包、`raw_data.csv`、`raw_codebook.csv`，并能读取。

执行线程要先判断当前 bookapp 来源域名，再决定落盘方式。

#### localhost / 127.0.0.1

如果当前页面是 `http://localhost:8000/` 或 `http://127.0.0.1:8000/`：

- 不再把内置浏览器当作普通 Chrome 下载通道，也不反复去系统 Downloads 里找文件。
- 在完成页面检索、变量详情理解、变量选择、预览和点击下载之后，执行线程根据本次页面已选变量，优先调用 `recover_bookapp_export.py --latest` 自动匹配最新下载记录，并调用 bookapp 后端同一套导出逻辑，把这次导出的 zip/raw 恢复到正式项目目录。
- 若 `--latest` 无法确认本次记录，才回退个人中心人工读取 transaction id；回退原因必须写入过程卡和踩坑复盘包。
- 恢复输入必须来自本次页面已选变量，使用 bookapp 显示名与变量名一一对应的清单。
- 这一步只用于本次 raw 包落盘，不能用于发现变量、替代变量理解或跳过网页流程。
- 恢复后仍要检查正式目录中 `bookapp_download.zip`、`raw_data.csv`、`raw_codebook.csv` 是否真实存在且可读取。
- QA 文本或运行日志写明：“本次在 localhost bookapp 中完成选择并点击下载；执行线程按本次页面已选变量用 `--latest` 自动匹配下载记录，并调用同一导出逻辑将 zip/raw 恢复到正式目录。”发布笔记摘要不讲下载补救过程。

#### dbcodebook.cn 正式域名

如果当前页面是 `https://dbcodebook.cn/` 或其他正式线上域名：

- 按真实用户下载处理，不调用本机 localhost 后端恢复包。
- 优先使用浏览器实际下载文件；若 Codex 内置浏览器不可见下载文件，由用户提供或指定已经下载到本地的 zip/raw 文件位置。
- 执行线程只把这次正式域名下载得到的本地文件复制/解压到正式项目目录，不从旧导出、底层 DB 或 Parquet 重新取数。
- QA 文本或运行日志写明正式域名来源、本地文件路径和落盘时间。

无论哪种来源，正式定义只能基于本次 bookapp 页面流程确认过的变量和最终落到正式项目目录的 `bookapp_download.zip`、`raw_data.csv`、`raw_codebook.csv`。

## 5.0 正式 R 脚本运行规则

执行线程生成 R 脚本后，验证对象只能是正式成果目录中的那一份 `define_charls_xxx.R`。

正确运行方式：

1. 工作目录切到正式成果目录，例如 `<DBCODEBOOK_HOME>\演示\定义\CHARLS_xxx`。
2. 直接运行正式脚本文件，例如 `Rscript.exe define_charls_xxx.R`。
3. 把完整控制台输出保存为 `CHARLS_xxx_run_YYYYMMDD.log`。
4. 若脚本报错，先判断是定义代码错误，还是执行线程 R 环境与用户可运行环境不一致。
5. 只有确认是定义代码错误时，才修改正式 R 脚本；修改后仍然重新从头到尾运行同一份正式脚本。

不允许把下面行为当作“脚本已运行”：

- 只运行临时代码片段。
- 只抽查 `raw_data.csv`。
- 只运行环境预检。
- 在正式脚本外单独安装包后继续说脚本已验证。
- 临时复制/改写一份脚本去跑，正式脚本没有同步更新。
- 因为执行线程环境缺包，就把正式脚本改成环境安装脚本。

最终收口时必须说明：

- 是否直接运行了正式 `define_charls_xxx.R`。
- 运行目录是什么。
- 使用的 R/Rscript 是哪一个。
- 日志文件是哪一个。
- 如果没有直接跑通，原因是代码错误、环境未对齐，还是用户决定手动运行。
## 5. R 代码风格

变量定义脚本必须沿用用户已确认的项目 R 风格；历史参考脚本见 `CHARLS数据库profile.md`，不得把参考脚本所属主题的变量口径套到新主题。

基本风格：

- `rm(list = ls())`
- 包检查块固定写在 `library()` 之前：
  ```r
  for (pkg in c("devtools", "openxlsx", "dplyr")) {
    if (!requireNamespace(pkg, quietly = TRUE)) {
      install.packages(pkg)
    }
  }
  ```
- 包加载块包含 `devtools`、`openxlsx`、`dplyr`
- `library("dbCodeBookr")` 前一行固定写：
  ```r
  install_github("ZhidoHuang/dbCodeBookr") # 提示更新包, 可选3跳过，首次使用时需要安装
  ```
- `library("dbCodeBookr")` 是必备项
- `dt <- read.csv("raw_data.csv")`
- `name_z <- read.csv("raw_codebook.csv")`
  - CHARLS 导出与恢复工具必须提供不带 BOM 的 UTF-8 CSV；公开 R 不增加编码或列名参数，也不事后修补首列名。不同 File 或模块出现同名 raw 时，必须在 dbCodeBook 变量选择阶段按来源身份设置唯一别名，预览确认表头唯一后再下载；正式 R 不使用 `check.names = FALSE`，也不按列位置重命名。
- `data <- dt`
- `data[data == ""] <- NA`
- 不默认写 `data[data == "null"] <- NA`
- 不默认写泛化 `normalize_text <- function(x) { ... }`；需要清理时按具体变量处理
- 读取区不写 `raw_row_count`、全局目标周期筛选、`raw_vars <- name_z$newname` 或防御式 `if (!"id" %in% names(data))`。
- QA 行数在 `# 输出` 后直接由 `nrow(dt)` 取得。
- raw 确含非目标调查年份时，只在正式输出边界明确排除；不要把研究样本边界伪装成读取步骤。
- 家户来源确实没有 `id` 时，直接按已核验规则由 `ID` 派生，并写清来源；不使用猜测式兜底分支。
- 每个关键变量先 `table(..., useNA = "ifany")`
- `dbCodeBookr` 函数、用户版笔记和代码注释遵守 `<SKILL_ROOT>\references\user-material-rules.md`
- 公开 R 在第一组主题 raw 清单、helper 或定义代码之前，必须先满足该规范 1.1.1 的“公开 R 业务背景合同”；只有章节标题、裸变量清单或实现型注释不算交代背景。
- 针对具体变量且紧邻重编码的 `table()` 可以进入公开主线；仅用于核对导出顺序、批量扫描标签或内部一致性的 `stopifnot()`、循环 `table()` 和类似检查放到 `# 输出` 后。
- R 代码中 `# 输出` 之前会进入用户笔记，展示从读取 raw、定义变量到正式输出的公开代码主线。
- `# 输出` 之后放 QA、HTML、笔记拼装、可视化 helper、`format_n()`、`safe_coverage_long()`、`make_dist_lines()`、`to_html_inline()` 等后台材料代码。
- `library("tidyr")` 只有在 `# 输出` 前核心定义确实需要时才前置；若只服务 QA 长表、HTML 或可视化汇总，应放在 `# 输出` 之后。
- 字符重编码按 `dbCodeBookr::recode.chr()` 的代码生成风格写：先对具体变量生成代码，例如 `recode.chr(data$bd001_clean)`；只有最终转换仍对同一个 `data$bd001_clean` 逐项枚举真实原值时，正式脚本才保留紧邻的 `# recode.chr(data$bd001_clean)` 和 `data$bd001_clean <- case_when(...)`。跨年份合并、多变量计分、汇总、阈值、回溯、正则或其它自定义逻辑不得贴 `recode.chr()` 标签。
- 数值重编码按 `dbCodeBookr::recode.num()` 的代码生成风格写：只有函数确实针对同一变量生成数值转换时，才保留 `# recode.num(data$var_clean)`，下一条非空代码必须继续赋值给 `data$var_clean` 并使用它自身的原值。已经计算完成的得分、合计变量、跨年份统一变量和阈值变量不贴 `recode.num()` 标签。正式 Rscript 不依赖 `recode.chr()` / `recode.num()` 的运行期返回值完成转换。
- 多个候选变量按优先级合并时，优先使用 `yyds_coalesce()`；不要手写一长串 `case_when(!is.na(...))`，除非该逻辑无法用 `yyds_coalesce()` 表达。
- `case_when(...)` 可以作为 `recode.chr()` / `recode.num()` 生成后的固化代码，也可以用于无法直接用 recode/coalesce 表达的条件判断。若 `case_when()` 中使用 `grepl()`、区间判断、跨变量条件、回溯逻辑等，它就是自定义清洗/定义逻辑，不得标为 `recode.chr()` 生成代码。
- 定义笔记与正式业务 R 不显示 `raw_data.csv` 的网站获取提示；该提示只由公众号 SVG / 富文本公共工具在宣传代码展示层注入，不得从宣传反写定义源。
- 每个派生变量生成后再次 `table()` QA
- 用 `add_mapping()` 记录派生变量来源
- 用 `write.xlsx(..., overwrite = TRUE)` 输出完整 db/codebook 和 analysis 文件，避免旧文件没有被覆盖。
- 不为了说明波次范围或路由来源创建纯副本变量，例如不要写 `data$da061_w1_4 <- data$da061`；如果只是统一标签或清洗同一个原始概念，直接清洗原变量，避免无意义中间变量进入 `data`、codebook 和网页详情。

### 5.0.1 Codex 沙箱下的 R 用户库权限

本机 R 包安装在用户库时，常见路径为：

```text
<USERPROFILE>\AppData\Local\R\win-library\4.4
```

Codex 普通沙箱可能无法读取该用户库，表现为：

- PowerShell 能看到用户库目录和包。
- 普通沙箱下的 `Rscript` 中 `.libPaths()` 可能只包含 `<R_INSTALLATION>\library`。
- `library("devtools")`、`library("openxlsx")`、`library("dplyr")`、`library("tidyr")`、`library("dbCodeBookr")` 报缺包。

这不是正式 R 脚本错误，也不等于需要安装包。处理顺序：

1. 先用提升权限检查 R 是否能看到用户库和关键包。
2. 如果提升权限下 `.libPaths()` 包含用户库，且关键包可用，则在正式成果目录中用提升权限直接运行同一份 `define_charls_xxx.R`。
3. 运行日志写入正式目录，例如 `CHARLS_xxx_run_YYYYMMDD_HHMM.log`。
4. 不把安装包、`.libPaths()` 修改、用户库创建写进正式定义脚本。
5. 不把“普通沙箱缺包”收口为“让用户自己运行”。

本规则解决的是 Codex 执行权限问题，不改变用户的 R 代码习惯。
## 5.1 自定义映射规则

`add_mapping()` 不能只映射到上一层派生变量，要追溯到参与定义的来源变量。

错误示例：

```r
map <- add_mapping(map, "A_x_final", c("A_x_intermediate"))
```

正确示例：

```r
map <- add_mapping(map, "A_x_final", c("raw_var1", "raw_var2", "A_x_intermediate"))
```

原则：如果一个变量由多个原始变量和中间派生变量共同定义，映射中要写出这些来源，不能让 codebook 在中间层断掉。

codebook 生成时也要保留这些映射来源：如果某个来源变量不在 `raw_codebook.csv` 中，例如中间派生变量 `A_x_intermediate`，也要保留在 `processed_vars/original_vars`，不能因为匹配不到 raw codebook 就丢掉。

## 5.2 命名规则

变量名要简短清晰，优先使用稳定含义词，不把过程词和解释词塞进变量名。

新变量命名前必须检查现有正式变量中是否已有同一研究概念系列；有明确系列关系时复用共同前缀，并在候选阶段一次性确认相关既有变量是否需要同步命名或下游刷新，避免正式生成后再返工。

命名示意：

- `A_x_raw`：原始分类文本。
- `A_x`：主要分析变量。

## 6. 编码规则

只有 YES/NO 二分类变量使用 `1/0` 数值。

正式分析变量的分类编码默认使用英文/ASCII，便于跨数据库分析、建模和后续脚本复用；中文可以写在 R 注释、Criteria、QA 或笔记解释里。只有用户明确要求中文编码时，才把中文作为正式取值。

允许使用 `1/0` 的例子：

- `A_x_yesno`
- `A_x_any`

其它分类变量必须保留解码后的文字标签，不额外生成 `1/2/3` 数值分类。

YES/NO 二分类变量不额外生成 `_label`、`_text` 这类过程解释变量；`1/0` 的含义写进 codebook。

不保留纯过程副本变量。若某个对象只是原变量的重命名副本或过渡副本，应使用临时局部对象或直接清洗原变量，不进入最终 `data`。

例如：

```text
A_x_status
  Category A
  Category B
  Category C
```

不再生成：

```text
A_x_status_num = 1/2/3
```

### 高位异常编码检查

遇到数值型变量、时间、频次、金额、时长、计数、总分或连续换算变量时，必须检查 `997`、`998`、`999` 这类高位编码是否为特殊编码。

- 不得默认把 `997`、`998`、`999` 当作真实数值进入连续变量计算、均值、总分、MET、时间换算或计数加总。
- 必须结合官方问卷详情、raw_codebook 和 raw 分布判断它们是“不知道 / refused / missing / not applicable / other special code”，还是问卷允许的真实数值。
- 若官方说明这些值是特殊编码，应重编码为 `NA` 或按题意处理，并在 QA 中披露原始出现次数和处理方式。
- 若官方说明这些值是合法真实值，才可保留为数值，并在 QA 中说明保留依据。
- 对普通分类变量，`997`、`998`、`999` 也应作为特殊选项核查；不得不经判断直接当作普通等级或普通类别。
- 自检 / QA 至少报告参与定义变量计算的 raw 变量中 `997`、`998`、`999` 的出现次数、是否参与计算、最终处理方式。

如果轻量扫描发现既有主题可能把这些值带入正式连续计算，执行线程应先回大脑裁决，不得自行改变变量口径。

## 7. 输出规则

主交付只保留 xlsx：

- `db_A_xxx.xlsx`：全量数据加定义变量。
- `codebook_A_xxx.xlsx`：全量变量说明。
- `analysis_db_A_xxx.xlsx`：只保留分析变量。
- `analysis_codebook_A_xxx.xlsx`：只保留分析变量 codebook。

呈现交付需要同步生成：

- `CHARLS_xxx_detail.html`：网页详情长表材料。
- `CHARLS_xxx_definition.html`：最终定义变量网页详情材料。

detail / 组分概览覆盖热力表的 `wide_data$category` 只服务展示分组，不改变正式数据或变量口径。该字段必须按变量实际定义结构归类：

- 不允许把明显属于多个概念、模块或变量组的变量统一写成一个笼统 category，例如 `Hukou and live urban-rural`、`Education`、`Health`。
- 同一概念的 raw 变量和对应最终分析变量放在同一 category。
- 多概念主题要拆成多个 category；单概念主题可以只保留一个 category，但名称也应具体到主题/变量组，而不是泛泛模块名。
- 推荐使用显式映射实现，例如 `case_when()` 或命名向量，不要一行统一赋值。
- 必须设置未预期变量兜底：未匹配变量归为 `Other / check` 或同等警示 category，并触发 warning 或写入 QA/过程卡，避免静默错分。
- 正式回传和验收应确认 `Other / check` 是否出现；如果出现，必须说明原因或返修。
- 多概念主题的 detail HTML / 笔记覆盖热力表应出现多个 category，不应出现笼统合并 category。

QA/解释交付需要同步生成：

- `CHARLS_xxx_QA.txt`：内部 QA 与披露文本，合并原始变量情况、跨年份含义漂移、变量取舍理由、定义逻辑、关键 QA 和原始矛盾披露。

## 7.1 笔记正文拼装规则

变量定义任务收口时，需要把可发布笔记拼成一个 `.md`，不要让用户在多个 HTML、R 脚本和 report 之间手动拼。

固定结构：

```text
## 摘要导读
## 定义
  CHARLS_xxx_definition.html 的完整内容
## 材料
### 1-提取变量
  custom-textbox，按 `bookapp显示名=变量名` 列出本次选择的原始变量，并保留 `Go to 提取变量` 按钮
### 2-代码材料
  fenced code block，放发布版 R 代码：从读取 raw、定义变量到正式输出为止，在 `# 输出` 前截断；不放 QA、HTML、笔记拼装和可视化 helper
## 定义的组分概览
## 定义的组分详情
  CHARLS_xxx_detail.html 的完整内容
```

摘要导读的内容、语言、五列表字段和覆盖率表达统一遵守 `<SKILL_ROOT>\references\user-material-rules.md` 中的“笔记摘要导读内容规则”。本流程只规定上述笔记章节顺序，不维护第二套摘要写作规则。

摘要与 `Criteria` 都必须从正式 R 生成源刷新；不得只修改最终笔记。固定检查器核对结构、正式事实和同步关系，不以禁词、句子差异或改写比例判定语言质量。

材料规则：

- `1-提取变量` 使用固定 `custom-textbox` 结构，必须包含两部分：`<div class="textbox-content">` 中的 `bookapp显示名=变量名` 列表，以及 `<button class="textbox-button" onclick="goToExtractVariables(this)">Go to 提取变量</button>` 按钮。
- `textbox-content` 不能只写裸变量名，必须使用 `bookapp显示名=变量名`，例如 `da059 (health status and functioning)=da059`；这样 `Go to 提取变量` 才能正确定位变量。
- `1-提取变量` 禁止保留占位符 `请在这里输入文本框内容`。用户材料迁移、回传和验收时，必须扫描最终 `*_笔记.md`：`Go to 提取变量` 出现 1 次，占位符出现 0 次，变量列表非空；如需修正，必须从正式 R 的 `extract_box` / `note_lines` 源头修，不得手工只改生成后的 md。
- `2-代码材料` 只放发布版 R 代码：从读取 raw、定义变量，到正式输出为止；不要把 QA、report、HTML 详情、笔记拼装、可视化 helper 等后台生成过程放进发布笔记。
- `2-代码材料` 不要手工另放“目录式小标题”。
- 页面会根据 R 代码中的 `# ----------- ... -----------` 和 `## ... ####` 自动生成代码目录。
- `定义`、`定义的组分概览`、`定义的组分详情` 使用 R/dbCodeBookr 生成的 HTML，不手写重造。
- 笔记中 detail / 组分概览部分只允许出现一个标准标题：`## 定义的组分概览`。禁止残留旧过程标题或序号标题，例如 `### 3-详情材料`、`3-详情材料`、作为章节壳的 `详情材料`；也禁止重复出现 `## 定义的组分概览`。
- 用户材料迁移、回传和验收时，必须扫描最终 `*_笔记.md`：旧标题壳计数为 0，标准标题 `## 定义的组分概览` 计数为 1。若不符合，必须从正式 R 的 `note_lines` / 笔记拼装源头修正，不得手工只改生成后的 md。

文本沉淀边界：

- `CHARLS_xxx_QA.txt`：内部沉淀，记录原始变量情况、定义逻辑、QA、矛盾披露和下载异常说明。
- `CHARLS_xxx_笔记.md`：面向 bookapp 发布的完整正文，也是唯一常规 Markdown。
- 不再额外生成 README、report、closeout、logic summary、consistency disclosure 等零散 md；除非用户明确要求。

## 8. QA 规则

至少做三层 QA：

1. 原始变量 QA：
   - `table(raw_var, year, useNA = "ifany")`
   - 对同名变量跨年份漂移做年份限制后再 table，避免无关文本刷屏。

2. 派生变量 QA：
   - `table(A_var, useNA = "ifany")`
   - `table(A_var, year, useNA = "ifany")`
   - 每个最终分析变量都要按年份检查非缺失数和缺失数；如果某一年明显骤降，必须解释是问卷路由、变量缺失、定义过严、下载问题，还是原始数据问题。
   - 对 `ever` 这类“历史状态”变量，不能只看当前波次是否为 yes；必须确认 non-current 人群是否有历史来源。若没有历史来源，不得把过去一年不发生直接推断为从未发生。

3. 输出文件 QA：
   - 读取 `analysis_db_*.xlsx` 检查列名。
   - 读取 `analysis_codebook_*.xlsx` 检查变量名。
   - 确认分类变量为解码文本，YES/NO 变量为 `1/0`。
   - 确认没有不需要的 CSV/RDS。

- 官方问卷详情文本定位失稳时，可以使用截图定位 + 可见区域坐标点击作为 fallback；过程卡必须记录截图路径、页面路径、变量名、单元格/字段和核验结论，不能只写“已确认”。

### 2. 正式 R 运行器

正式 R 脚本统一优先使用：

```powershell
& <SKILL_ROOT>\scripts\run_r_definition.ps1 `
  -WorkDir "<正式成果目录>" `
  -Script "<正式R脚本名>" `
  -LogPrefix "<日志前缀>" `
  -ArchiveDir "<过程目录>\archived_logs"
```

要求：

- 运行对象必须是正式目录中的同一份正式脚本。
- 正式 R 脚本必须是 UTF-8 without BOM；`run_r_definition.ps1` 会在启动 R 前检测 UTF-8 BOM，发现后直接停止，执行线程必须先修正编码。
- 工具会捕获 stdout/stderr，避免 PowerShell 把 R 包加载 stderr 包装成 `NativeCommandError`。
- 工具会在日志尾部写入 `Rscript exit code: 0`。
- 正式目录只保留一个最终成功日志，旧日志进入过程目录 `archived_logs`。
- 执行线程不得把没有明确退出码的 log 标记为机器闸门通过，也不得提交独立验收。

### 3. 定义成果自检器

执行线程回传审核包前，必须优先使用：

```powershell
python <SKILL_ROOT>\scripts\check_definition_output.py `
  --formal-dir "<正式成果目录>" `
  --raw-vars "<raw变量逗号列表>" `
  --analysis-db "<analysis_db文件名>" `
  --analysis-columns "<analysis_db列名逗号列表>" `
  --analysis-codebook "<analysis_codebook文件名>" `
  --analysis-vars "<分析变量逗号列表>" `
  --forbid-vars "<禁止变量逗号列表>" `
  --log-prefix "<日志前缀>" `
  --require-log-exit-code
```

自检至少覆盖：

- 禁止产物：`*_defined.csv`、`.rds`、单独 consistency disclosure xlsx、多余 md、多余 log。
- `raw_data.csv` header 和 `raw_codebook.csv` 变量清单。
- 禁止变量是否误入 raw、codebook、analysis_db。
- `analysis_db` 列名与维度。
- `analysis_codebook` 分析变量列表。
- 最终日志是否唯一、是否含 `Rscript exit code: 0`、是否含 `NativeCommandError` 或 `Execution halted`。

自检失败时，执行线程必须先自行修正机械问题；不得入账，也不得把明显未收口的成果交给独立验收。

### 4. 任务启动模板

每个定义任务开工时，过程目录必须创建或更新：

```text
<DBCODEBOOK_HOME>\演示\定义\_执行线程\{数据库}\{主题编号}_{主题名}\current_task.md
```

模板位于：

```text
<SKILL_ROOT>\assets\current-task-template.md
```

开工卡必须写清：

- 正式目录、过程目录、旧目录只读边界。
- 本轮变量前缀、预计最终变量、禁止变量。
- bookapp 目录路径、官方问卷详情核查点、预览 header。
- raw 恢复命令、R runner 命令、自检器命令。
- 回传成果审核包和字段化踩坑复盘包的要求。

### 5. 大脑派发要求

大脑派发定义任务时，默认写入以下硬闸门：

- 使用新干净 bookapp 标签。
- 使用 `recover_bookapp_export.py` 恢复 localhost raw。
- 使用 `run_r_definition.ps1` 正式运行 R。
- 使用 `check_definition_output.py` 做执行线程自检。
- 自检通过后才回传审核包。

除非任务明确不涉及 R 或正式成果目录，否则不得跳过这些闸门。

## 2026-06-29 执行流程回顾与复发阻断规则

本节用于阻断“上一个流程踩过的坑，下一个流程继续踩”。定义执行线程不能只在任务结束后写复盘，必须在开工、执行中、回传前三个节点做流程回顾。

### 1. 开工前回顾已知坑

每个定义任务创建 `current_task.md` 时，必须填写“上轮坑回顾”。

来源包括：

- 最近 1-2 个同数据库定义任务的过程卡和踩坑复盘包。
- 当前数据库 profile 或 CHARLS 标准流程中已经沉淀的规则。
- 大脑派发任务包中的硬闸门。

必须写明：

- 哪些已知坑与本任务相关。
- 本轮具体用什么动作预防。
- 是否已经落实到命令、工具或检查项。

没有“上轮坑回顾”的过程卡，视为未完成开工准备。

### 2. 执行中及时上报新问题

执行线程遇到以下情况，不能等最终审核包才说：

- 阻断定义边界的问题：立即暂停并回报大脑。
- 已知坑复发：立即在过程卡标记为“复发”，并说明既有规则为什么没有挡住。
- 高复发机械问题：当前任务可继续，但必须在过程卡写明建议沉淀为流程、模板或工具。
- 单一低复发问题：记录在过程卡，可不进入通用流程。

已知坑复发时，不能只说“本次已解决”。必须额外回答：

- 为什么上次沉淀没有防住？
- 是流程没写、任务包没派、工具不好用，还是执行线程没按规则做？
- 本次建议怎么改流程/模板/工具？

### 3. 回传前做复盘闭环

执行线程回传成果审核包前，必须同时回传“执行流程复盘包”。它是踩坑复盘包的升级版，固定包含两部分：

1. 已知坑回顾结果：
   - 已知坑是否复发。
   - 没复发的原因：用了哪个工具或规则挡住。
   - 复发的原因和补救建议。
2. 本轮新增坑：
   - 当前任务名。
   - 坑的类型。
   - 具体发生了什么。
   - 为什么发生。
   - 本次怎么解决。
   - 是否可能复发。
   - 建议沉淀位置。
   - 建议新增的流程规则或工具化动作。

缺少执行流程复盘包，任务不得标记完成；如命中风险触发器，也不得发送独立验收。

### 4. 大脑处理责任

大脑收到复盘包后不能只转述结果，必须做裁决：

- 高复发且可工具化：派发工具化任务或直接更新工具。
- 高复发但不适合工具化：写入标准流程或任务模板。
- 数据库特异问题：写入数据库 profile 或主题过程卡。
- 低复发问题：明确标记“不沉淀，仅留过程卡”。

如果同一问题第二次复发，大脑必须优先处理流程/工具缺口，暂停继续批量定义。

### 5. 机器闭环与异常验收

执行线程完成机器闭环时必须检查：

- `current_task.md` 是否有“上轮坑回顾”。
- 回传包是否包含“已知坑是否复发”的明确判断。
- 已知坑复发时，是否给出流程/工具修复建议。

若缺少这些内容，不得标记 `MACHINE_CHECK_PASS`。只有机器证据冲突、研究问题未决、公共核心机制边界不足或用户/大脑明确要求时，才启动限定范围独立验收。

## 2026-06-29 QA 与 raw 读取补充规则

- CHARLS raw 常同时包含 `ID` 与 `id`，PowerShell 对对象属性名大小写不敏感，`Import-Csv` 会发生字段冲突；不得用 PowerShell `Import-Csv` 读取这类 raw。临时 QA / 自检脚本优先使用 Python `csv`、R `read.csv(check.names = FALSE)` 或既有自检器；正式定义 R 脚本仍按通用规范默认直接 `read.csv("raw_data.csv")`。
- QA 汇总中不要用输入列名作为 `summarise()` 输出列名；使用 `*_count`、`n_*` 等明确名称，避免输出列遮蔽原列导致统计错误。关键 QA 表需抽查一致性。
- 同名前缀变量（例如 `db010`、`db011`）可能在不同年份对应不同问卷题或路径题；跨波次定义时不得只看搜索结果 Easy label，必须逐年点击官方问卷详情说明核验，并在脚本中用 `year` 条件显式区分语义漂移。
- 关键 QA 表（覆盖率、映射检查、缺失专项、特殊路径题检查）优先生成固定 Markdown 表或等价稳定文本，不依赖 tibble/console 默认打印；验收报告需要能直接读取到完整列名和关键数量。

## 2026-07-03 定义过程卡证据链索引规则

每个定义任务的 `current_task.md` 必须固定包含小节：`## 证据链索引`。

该小节只做索引，不写成长篇验收报告。目的不是替代 QA 或机器报告，而是让大脑和按需启动的独立验收任务快速定位本轮定义的关键证据。

### 1. 必须索引的证据

`## 证据链索引` 至少包含以下路径或摘要：

- bookapp / 官方问卷详情截图路径。
- bookapp 页面路径与目录路径。
- 候选变量与最终 raw 变量清单。
- 被排除变量及排除理由。
- 下载/恢复证据：transaction id 或 `--latest` 匹配结果、recover QA 路径、`raw_data.csv` 路径、`raw_codebook.csv` 路径。
- 正式脚本路径、最终 log 路径、自检 JSON 路径。
- QA、definition HTML、detail HTML、笔记路径。
- 大脑裁决或用户裁决摘要，如本轮发生过变量边界、命名、编码、下载重做等裁决。
- 验收报告来源线程和状态摘要，如已进入验收闭环。

### 2. 过程材料与用户材料边界

证据链索引是内部流程材料，只写入过程卡和执行/验收回传包。用户版笔记、definition HTML 和 Criteria 只吸收必要背景解释，不承载完整内部证据链。

不得因为过程卡新增证据链索引，就把 `transaction`、`recover`、`自检`、`验收`、`见 QA`、`正式目录`、`过程目录` 等内部词汇带入用户可见笔记或 definition Criteria。

用户版笔记摘要可以按共享“笔记摘要导读内容规则”说明真实执行的 dbCodeBook 普通检索关键词或完整目录入口、数据库相关内容和本次正式选取条数；目录面板筛选词不作为普通检索关键词写入。这属于读者可理解的检索背景，不属于内部制作过程。除此之外，用户版笔记、definition/detail HTML 正文、Criteria 和公开 R 代码注释只写数据对象、变量语义、年份逻辑、必要的来源差异和研究使用影响，不得交代“按用户脚本/代码”“bookapp/工具”“本轮/旧版/旧口径/撤回/重建”等制作来源、历史过程或实现决策。多来源同名、导出别名或冲突处理应写成中性数据说明，例如说明不同模块均有同名记录、为区分来源使用别名、来源不一致时保留冲突标记。

写入用户材料前，每一句都必须通过三问：是否帮助读者识别研究对象、适用范围或变量含义；是否帮助读者复现或审视数据逻辑；是否会改变读者的分析选择、可比性判断或结果解释。三者皆否的内容应留在过程卡、证据链索引或 QA，不进入笔记、Criteria、HTML 正文或公开 R 代码注释。词组扫描只能作为辅助守门，不能替代这三问判断。

### 3. 机器核验与触发验收

执行线程在机器闭环时应检查 `current_task.md` 是否存在 `## 证据链索引`，以及索引是否能定位到本轮截图、raw 恢复、正式脚本、最终 log、自检 JSON、QA/HTML/笔记和裁决/验收状态。命中风险触发器时，独立验收任务复核相关路径。

缺少该小节或关键路径明显缺失时，可打回定义执行线程补过程卡；该类补充不应改动正式成果目录，除非发现正式成果本身确实缺失。
