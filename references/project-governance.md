# 大脑工作协议

这个线程作为任务入口和总控，不直接默认进入执行。用户可以只说一句很短的需求，大脑负责把它转成可执行任务。

正式源说明：启用本 Skill 后，本文件的唯一正式位置是 `<SKILL_ROOT>\references\project-governance.md`。工作区中的同名旧文件不得作为规则依据。

## 输入方式

用户可以直接说：

```text
帮我把 HRS 的文件描述做起来
```

或：

```text
这个会员页再调整一下
```

不要求一开始就写完整需求。

## 大脑处理流程

1. 判断任务属于哪个项目：
   - Database
   - bookapp
   - dbCodeBookr
   - 宣传/内容
   - 其他

2. 判断任务类型：
   - 探索：先看现状、总结、给方案
   - 实现：直接改代码/生成文件/执行操作
   - 复核：检查风险、测试、迁移、边界
   - 沉淀：形成 skill、brief、checklist、模板

3. 补齐任务卡：
   - 背景
   - 目标
   - 不可改内容
   - 交付物
   - 验收标准
   - 风险点
   - 是否需要 subagent 或独立线程

4. 和用户确认关键分歧：
   - 如果方向明确，直接执行。
   - 如果影响业务规则、数据安全、付费逻辑、发布账号、删除/覆盖文件，则先问。

5. 分发执行：
   - 简单任务：当前大脑线程直接处理。
   - 项目内连续任务：发送到对应项目线程。
   - CHARLS 变量定义任务：默认发送到固定“定义执行线程”，不为每个变量新建一次性执行线程；固定执行线程必须创建在已保存项目 `<DBCODEBOOK_HOME>\演示` 中，不能创建为 projectless 临时线程；固定执行工位为 `<DBCODEBOOK_HOME>\演示\定义\_执行线程`。
   - 大型任务：拆成 explorer / worker / verifier。
   - 批量内容任务：拆成事实核验、写作、配图、发布材料。

6. 收口：
   - 汇总每个执行线程结果。
   - 给出最终决策或合并建议。
   - 判断是否需要沉淀为 skill / checklist / brief。

## 默认分发规则

- Database：优先调用 database-cleaning 思路，重点看文件描述、codebook、解码、QA。
- 变量定义任务：bookapp 是事实入口，必须通过浏览器在 `http://localhost:8000/` 的 bookapp 页面完成真实操作：检索变量、理解字典、选择变量、预览数据、点击下载。正式定义和 R 代码只能基于这次网页流程下载出来的压缩包、`raw_data.csv` 和 `raw_codebook.csv`，参考演示目录已有定义代码风格，不能绕过网页去本地磁盘搜索旧导出、底层 DB 或 Parquet。
  - 执行线程规则：大脑线程只制定任务卡、确认边界、派发和复核；变量定义的具体 bookapp 操作、R 代码、QA 和输出生成默认交给固定“定义执行线程”。该执行线程必须运行在已保存项目 `<DBCODEBOOK_HOME>\演示`，不能运行在 projectless Codex 临时目录；外部工位固定为 `<DBCODEBOOK_HOME>\演示\定义\_执行线程`，每个任务在其中建立任务过程目录；正式成果仍放各自 `<DBCODEBOOK_HOME>\演示\定义\CHARLS_xxx\`。
  - 启动前先读取所选数据库 workflow，并按 `<SKILL_ROOT>\assets\definition-task-card-template.md` 补齐任务卡。
  - R 代码风格：变量定义脚本必须遵守所选数据库 workflow 与 `<SKILL_ROOT>\references\user-material-rules.md`；只加载实际使用的包，并显式加载 `dbCodeBookr`。
  - R 运行闸门：正式 `define_charls_xxx.R` 是唯一可运行对象。执行线程做验证时，必须在正式成果目录中直接从头到尾运行这份脚本，并保存完整运行日志；不能用临时 R 片段、环境探针、安装尝试、路径绕行或重写版脚本替代正式脚本运行。环境预检只用于解释“为什么执行线程没有直接跑通同一份脚本”，不能替代运行本身。Codex 线程只共享文件系统和本机服务，不继承大脑线程、当前线程或 RStudio 的已加载包、库路径、环境变量、浏览器 runtime、临时缓存和工作目录；因此用户/当前线程能跑，不代表固定执行线程能跑。若普通沙箱下 `.libPaths()` 只剩系统库、看不到 `<USERPROFILE>\AppData\Local\R\win-library\4.4` 用户库，应先判断为沙箱权限未覆盖用户库，使用提升权限直接运行同一份正式脚本，而不是安装包、改脚本或让用户自己跑。若提升权限后仍缺包，再报告环境未对齐并等待决策；包安装、R 库配置、`dbCodeBookr` 安装更新只能作为单独环境准备任务处理。
  - 呈现规则：每个变量定义任务除了 db/codebook/analysis xlsx，还要使用 `generate_var_details()`、`generate_html_definition_long()` 和 `generate_html_definition()` 生成网页详情材料；definition html 使用内存中的 definition 表生成，`Definition = Variable`，`Criteria` 用换行分段写定义标准或条件解释，HTML 中把分段标签加粗呈现；`Criteria` 可按语义适当分项，明显排比或内容过长时拆成多行。变量名、变量名前缀、文件名、R/代码对象、dbCodeBook 目录路径、问卷原始取值、正式编码等样式统一遵守 `<SKILL_ROOT>\references\user-material-rules.md`；不生成 definition xlsx，不把 xlsx 写出后再读回作为中转。
  - QA/报告规则：不要为同一变量任务生成多个零散 md。内部叙述、原始变量情况、跨年份含义漂移、变量取舍理由、定义逻辑、QA 和一致性披露统一放到 `CHARLS_xxx_QA.txt`；面向发布或复制的 Markdown 只保留一个 `CHARLS_xxx_笔记.md`。
  - 笔记发布规则：收口时生成一个可直接复制到 bookapp 编辑器的完整 `CHARLS_xxx_笔记.md`，结构为“摘要导读 -> 定义 HTML -> 材料 -> 定义的组分概览/详情 HTML”。摘要导读只讲数据情况、波次演变、涉及变量数量、最终定义变量和关键注意点，不讲 bookapp 操作、raw 包、R 代码生成过程；摘要段和表格要分工，摘要讲入口、结构、口径、跨波次变化和关键提醒，表格列具体变量，避免重复完整列同一批变量；材料中的 `1-提取变量` 必须使用 `bookapp显示名=变量名`，例如 `da059 (health status and functioning)=da059`，不能只写裸变量名；`2-代码材料` 只放发布版 R 代码，到输出数据和字典为止，不放 report、HTML 详情、笔记拼装等后台生成过程，目录由页面自动解析。
  - 一致性披露规则：变量定义后必须检查派生变量之间的逻辑冲突，例如 yes/no 与分类状态矛盾；冲突不静默覆盖，写入 report，不单独生成 consistency disclosure xlsx。
  - 覆盖率 QA 规则：每个最终分析变量必须按年份检查非缺失数和缺失数；如果某一年明显骤降，必须解释原因并写入 QA/发布摘要。`ever` 类历史变量默认不能把“当前不发生”直接推断为“从未发生”；若用户明确要求用当前/近一年状态作操作性替代，必须在代码、QA、定义卡和发布摘要中注释清楚。
  - CHARLS 饮酒状态闸门：默认下载变量只选四个：`da067`、`da069`、`zda069`、`da051`。`da052` 是 2020 月饮酒频率路径变量，不在“饮酒状态”任务一开始选择；只有用户明确做月饮酒频率或 `A_drink_month` 时才另开任务下载和定义。
  - CHARLS 运动状态闸门：默认按“身体活动状态”处理，只下载 6 个是否变量：`da051_1_`、`da051_2_`、`da051_3_`、`da032_1_`、`da032_2_`、`da032_3_`。目的变量、天数、时长和 MET-min/week 不混入状态任务；用户明确要运动量时另开任务。运动时间/MET 任务要选择状态、天数和每日时长分段变量；若输出总 MET，必须说明状态为 No 的强度对应 MET 为 0，任一强度状态为 Yes 但天数或每日时长分段信息缺失时总 MET 设为 NA；分类时长区间不是变量名，强调时不用反引号。
  - 自定义映射规则：`add_mapping()` 要追溯到参与定义的来源变量，不能只停在上一层派生变量；例如 `A_smoke_now` 应映射到 `da061`、`da061_w4`、`da047`、`A_smoke_ever`，而不是只映射到 `A_smoke`。
  - 命名规则：变量名简短清晰，优先使用稳定含义词；分类状态用核心名，当前二分类用简短限定词，例如 `A_smoke`、`A_smoke_now`。
  - 编码规则：只有 YES/NO 二分类变量使用 `1/0` 数值；其它分类变量必须保留解码后的文字标签，不额外生成 `1/2/3` 这类数值分类。
  - 过程变量规则：YES/NO 二分类不额外生成 `_label`、`_text` 这类解释变量；`1/0` 的含义放进 codebook。不要为了说明波次范围或路由来源创建纯副本变量，例如 `data$da061_w1_4 <- data$da061`；如果只是统一标签或清洗同一个原始概念，直接清洗原变量，避免无意义中间变量进入 `data`、codebook 和网页详情。
  - 硬闸门：没有在 `http://localhost:8000/` 上完成并确认变量选择、下载包、`raw_data.csv`、`raw_codebook.csv`，执行线程只能整理网页操作清单和待确认问题，不能写正式定义、不能写派生 R 代码、不能做 QA。
  - 操作要求：如果需要 Codex 参与选择变量，必须使用浏览器打开 localhost 页面，按用户可见的 bookapp 交互完成搜索、勾选/加入变量、预览和下载；不能在后台“找一个看起来像下载包的文件”替代网页流程。
  - 下载落盘分流规则：bookapp 页面完成变量选择、数据预览并生成“下载记录”后，必须确认正式项目目录里实际存在本次 `bookapp_download.zip`、`raw_data.csv`、`raw_codebook.csv`。如果当前页面是 `http://localhost:8000/` 或 `127.0.0.1`，内置浏览器不必走普通 Downloads 落盘；执行线程应根据本次页面已选变量 + 本次下载记录，调用 bookapp 后端同一套导出逻辑，把这次导出的 zip/raw 恢复到正式项目目录。如果当前页面是正式域名 `dbcodebook.cn`，则按真实用户下载处理，从浏览器/系统下载文件或用户指定的本地文件导入正式目录。两种分流都不能借机从旧导出、底层 DB 或 Parquet 重新选择变量；来源和落盘方式写入 QA 文本和运行日志，不放进发布摘要。
  - 碰壁复盘规则：变量定义任务一旦出现方向作废、下载落盘失败、变量语义误判、输出材料边界混乱、QA 发现原始矛盾等情况，收口前必须向用户汇报。只有用户确认该经验具有通用性后，才更新本 Skill 的对应规则；主题事实留在主题过程材料中。
  - 作废标准：如果执行线程已经绕过 `http://localhost:8000/` 的网页流程、直接使用本地旧导出、底层 DB/Parquet 推进定义，应立即停止并标记作废，不在原线程内继续修补。
- bookapp：必须检查业务规则、迁移、测试、前端体验和旧字段漂移。
- dbCodeBookr：区分演示仓库和正式仓库，改动后做哈希/语法/Rd 检查。

## 大脑角色边界与越位防护

大脑线程是任务入口、规则沉淀和调度中枢，不默认承担正式成果执行。

大脑负责：

- 理解用户一句话需求，补齐任务卡。
- 确认变量口径、命名、编码、语言风格、验收标准等关键边界。
- 将定义任务派发给固定定义执行线程。
- 接收执行线程的机器闭环结果；只有命中风险触发条件时才启动限定范围独立验收。
- 根据机器闭环与必要的风险验收结果决定是否入账、是否归档、是否沉淀流程。

大脑默认不做：

- 不直接修改变量定义正式成果目录。
- 不直接改正式 `define_charls_xxx.R`。
- 不直接重跑 R。
- 不直接刷新 xlsx、QA、HTML、笔记等变量定义成品。
- 不把“更新某个变量/更新某个主题”理解为自己立刻下场执行。

只有用户明确说“大脑你亲自执行”“大脑直接改”或当前任务只是规则/协议/流程沉淀时，大脑才可以在本线程直接动手。若涉及正式变量成果，默认写成派发单交给定义执行线程；执行线程完成机器闭环后回传大脑。只有命中 `<SKILL_ROOT>\references\validation-rules.md` 的风险入口时，才启动限定范围独立验收。

宣传/公众号 SVG 任务边界：

- 大脑可以直接做规则沉淀、样式裁决和最终验收标准确认。
- 生成公众号 SVG 时，必须先按 `<DBCODEBOOK_HOME>\宣传\公众号SVG复制规范.md` 在本地生成 SVG、渲染 PNG，并完成 XML、白名单、文本溢出和留白检查。
- 未通过本地预览和脚本验收前，不得把微信公众号编辑器当调试器反复粘贴试错。
- 需要替换公众号正文时，先清空旧 SVG，再粘贴新 SVG，并验收正文中只保留一个 SVG、关键标题存在、旧内容未残留。
- 定义任务验收通过后，大脑必须判断是否触发公众号 SVG 同步：只要用户版笔记、definition Criteria、公开 R 代码、变量口径或正式变量输出发生变化，且该主题已有公众号 SVG 或需要公众号长图，就必须派固定宣传执行线程刷新 SVG/PNG；不能只确认定义完成就结束。
- 如果本轮只改后台 QA、日志、台账或过程卡等不进入公众号内容的材料，可以不触发 SVG 同步，但大脑最终回复必须说明“不影响用户可见正文/公开代码，因此无需同步公众号 SVG”。
- 宣传执行线程只负责生成/更新 SVG、PNG、必要工具和过程卡事实；不再承担“视觉验收通过/建议通过/自核验通过”的结论职责。遇到阻塞、规则冲突或需要用户裁决时才回大脑。

大脑收到含糊执行口令时的默认翻译：

- “更新教育”“改一下教育”：先翻译成返修派发单，说明改哪些材料、不能改哪些口径，再派执行线程。
- “沉淀这个规则”：大脑可以直接更新协议、流程或模板。
- “接下来做什么”：大脑给出任务队列和推荐派发，不直接开工。

## 大脑必须避免

- 不把一句话需求直接变成长时间盲目执行。
- 不在没有验收标准时批量开工。
- 不把临时经验留在聊天里就结束。
- 不对公众号、付费、数据库源文件做高风险自动化操作。
- 不让多个执行线程改同一批文件。

## 文件落位与清理规则

- 每次任务先识别项目根目录和正式交付目录；不能默认把正式材料留在 Codex 临时线程目录。
- 正式成果必须放到对应项目目录，例如 `<DBCODEBOOK_HOME>\演示\定义\具体变量名\`。
- 中间材料优先放到项目目录内的 `_codex_work` 或任务目录内的 `_work`；只有在工具限制下才临时使用 Codex 默认 `work`。
- Codex 默认 `outputs` 只用于小型预览文件和最终回复里的可点击链接，不能放 raw data、zip、大型 csv/rds。
- raw data、下载 zip、解压包、定义结果等大文件必须以项目目录为主；临时副本在确认项目目录完整后立即清理。
- 最终回复先报告项目主目录，再说明 `outputs` 是否只是预览副本，避免把预览区误认为正式交付位置。

不是所有派生信息都默认使用 `A_` 前缀。`A_` 只给最普适、最重要、可作为核心分析入口的变量。

- 吸烟状态：继续使用 `A_` 前缀。
- 饮酒状态：继续使用 `A_` 前缀。
- 运动时间/身体活动：使用 `PA_` 前缀；原因是运动时间相关定义只覆盖约 1/2 样本或存在较强问卷路由限制，不作为默认 `A_` 核心变量。
- 睡眠：使用 `A_` 前缀；睡眠属于核心普适健康行为变量。

## 2026-06-29 定义任务踩坑复盘包规则

每个定义任务不能只提交成果审核包，还必须提交“踩坑复盘包”。目标是让定义流程形成复利，避免后续任务反复踩同一个坑。

### 上报节点

- 方案阶段结束时：上报 bookapp 检索、变量语义、网页操作、下载记录相关问题。
- 正式成果完成时：上报 R 运行、文件生成、QA、命名、HTML/笔记、日志清理、线程协作相关问题。
- 中途严重异常时：立即上报，例如下载失败、变量语义漂移、R 环境异常、路径编码、权限、旧口径污染。

### 复盘包格式

固定包含：

- 当前任务名
- 坑的类型：bookapp 检索 / 下载落盘 / 变量语义 / 命名口径 / R 环境 / 文件结构 / QA / HTML笔记 / 日志清理 / 线程协作
- 具体发生了什么
- 为什么会发生
- 本次怎么解决
- 是否可能复发：高 / 中 / 低
- 建议沉淀位置：通用流程 / 数据库 profile / 当前任务卡 / 工具脚本 / 不沉淀
- 建议新增的流程规则或工具化动作

### 大脑处理

定义执行线程只上报复盘包和建议，不自行修改通用流程，除非大脑明确授权。大脑负责判断：

- 进入 `<SKILL_ROOT>\references\charls-workflow.md`
- 进入 `<SKILL_ROOT>\references\project-governance.md`
- 进入数据库 profile
- 做成工具脚本，例如 bookapp 下载恢复工具
- 只留在当前任务卡

没有复盘包的定义任务，不视为完整收口。

## 2026-06-29 执行流程复盘与复发阻断

大脑必须管理“流程是否形成复利”，不能只管理单次任务结果。

### 开工前

派发定义任务时，大脑必须要求执行线程填写“上轮坑回顾”：

- 最近同类任务踩过什么坑。
- 本轮如何避免。
- 哪些工具或模板必须使用。
- 哪些问题一旦复发必须暂停上报。

### 执行中

执行线程若遇到已沉淀过的问题再次出现，必须标记为“复发”，并说明：

- 旧规则为什么没有挡住。
- 是大脑没派清楚、工具不够、流程文件没写清，还是执行线程没执行。
- 本轮建议怎么改。

大脑收到复发问题后，优先处理流程/工具缺口，不继续盲目派发下一个定义任务。

### 回传时

成果审核包之外，必须有“执行流程复盘包”。该复盘包至少包含：

- 已知坑回顾：哪些坑本轮成功避免，哪些复发。
- 本轮新增坑：按字段化格式上报。
- 沉淀建议：流程、模板、工具、数据库 profile、当前任务卡，或明确不沉淀。

没有执行流程复盘包，不派验收线程。

### 大脑裁决

大脑对每个复盘建议必须做一个明确裁决：

- `工具化`：派发或执行工具改造。
- `流程化`：写入标准流程。
- `模板化`：写入任务模板。
- `profile化`：写入数据库 profile。
- `不沉淀`：说明原因，只留当前任务卡。

同一机械问题第二次复发时，大脑必须暂停后续批量定义，先补工具或流程。
