# dbCodeBookr 函数与用户材料规范

版本日期：2026-07-27

适用范围：所有数据库变量定义任务，包括 CHARLS、ELSA、HRS、NHANES 等。各数据库标准流程必须引用本规范。

正式源说明：启用本 Skill 后，本文件的唯一正式位置是 `<SKILL_ROOT>\references\user-material-rules.md`。工作区中的同名旧文件不得作为规则依据。

## 1. 基本原则

- `library("dbCodeBookr")` 是变量定义脚本的必备包加载项。
- 代码要优先沿用用户已有 R 风格；各数据库或已完成主题的历史参考脚本见对应数据库 profile，不在本通用规范中写成固定主题规则。
- 正式分析变量的分类编码默认使用英文/ASCII；中文用于注释、Criteria、QA 或笔记解释。只有用户明确要求中文作为正式取值时，才把中文写入变量编码。
- QA 给研究者和验收线程看，可以包含覆盖率、缺失、冲突、内部来源、技术假设。
- 笔记给普通用户看，只写理解变量所需的信息，不写内部验收、常规缺失处理、流程动作和技术黑话。

## 1.1 公开 R 代码边界

正式 R 脚本中 `# 输出` 之前的代码会进入发布笔记，是用户会看到、会复制学习的公开代码。公开代码展示从读入数据、定义变量到正式输出的主线；`# 输出` 之后放 QA、HTML、detail、笔记拼装和可视化等后台材料生成代码。

`# 输出` 之前的公开代码段应包含：

- 环境初始化、包安装提示、包加载。
- 读取 `raw_data.csv` / `raw_codebook.csv`。
- 原始变量必要清理、逐项 `table()`、`recode.chr()` / `recode.num()` 风格重编码。
- 跨波次来源合并、回溯、派生变量生成。
- 正式输出代码，包括 `db_*`、`codebook_*`、`analysis_db_*`、`analysis_codebook_*` 的必要列选择和写出。
- 为正式字典和网页追溯服务的 `map <-`、`add_mapping()`、codebook 构建等代码。

`# 输出` 之后才放内部材料代码：

- QA 统计和报告文本。
- HTML / 笔记 / detail 页面生成。
- 可视呈现、格式化、排版 helper。
- `format_n()`、`safe_coverage_long()`、`make_dist_lines()`、`to_html_inline()` 等只服务 QA 或 HTML 的函数。
- `tidyr` 这类只服务 QA 长表或可视化汇总的包加载。

用户笔记里的 R 代码块默认截取到 `# 输出` 之前。不要把 QA、HTML、笔记拼装、可视化 helper 暴露在用户版代码材料里。

公开代码必须保留可供笔记目录/代码大纲提取的块级标题，统一使用 `# ----------- 标题 -----------` 格式。标题按读者实际阅读顺序覆盖环境与包、读取数据、主要清洗或重编码、核心派生变量、`# ----------- 变量字典 -----------` 和正式输出；复杂主题可按年份、来源或概念拆分主要处理段。变量字典标题下构造 analysis/raw 变量集合、正式数据与 codebook 的 Label、mapping 等内容。每个正式 analysis 变量都必须通过明确的 `map <- add_mapping(map, "变量名", raw_sources)` 登记全部参与定义的 raw 来源，并由 `map` 驱动 codebook 的 `original_vars`、`processed_vars` 与 `count`；不得直接手填这些 codebook 字段绕过 mapping。CHARLS 保留完整模块来源身份，ELSA 保留完整 `Variable (File)` 身份。标题必须紧邻并准确概括后续代码，不得添加没有对应代码的空标题。固定自检除检查代码块存在外，还要静态核验每个 analysis 变量的 `add_mapping()` 调用和 map 对 codebook 的实际驱动关系。

### 1.1.1 公开 R 业务背景合同

公开 R 服务于第一次接触该主题的普通读者。读取数据之后、第一组主题 raw 变量清单、自定义 helper 或定义代码出现之前，必须先用自然语言说明本次代码要完成什么。块级标题不能代替业务背景。

开头说明按主题实际情况覆盖以下内容：

- **研究任务：**原始问卷、测验或记录在询问/测量什么；读者需要知道数据对象和回答场景，不能只看到题号。
- **最终结果：**本次构造哪些正式变量，以及最基本的含义、计分方向、范围或变量间关系。
- **原始结构：**各周期、来源或题组怎样记录；如果前后期使用 checkbox、Yes/No、连续数值、上一轮预载、分项金额等不同结构，先说明差异，再列 raw 名称。
- **关键边界：**只有确实改变赋值或解释时，才说明特殊整组选项、完整性要求、冲突或必要缺失；普通空白不单独展开。

简单单题可以用 2-3 行说明；复杂量表、多周期测验或多来源汇总应按概念/周期分段说明。说明必须出现在相应代码之前，不能先写 `raw_vars <- ...`、矩阵、正则、循环或 helper，再让读者从后文反推目的。

raw 变量组第一次出现时，应就地标明它对应的周期和题目含义。类似 `old_word_vars`、`early_vars`、`parts` 的开发者命名不能独自承担解释责任。自定义 helper 保留时，前面还要用一句话说明其输入、输出及为何需要；若仍需跨多层函数才能看懂，应改成按周期、来源或题组展开的直线代码。

针对某个变量、紧邻重编码的 `table(data$var, useNA = "ifany")` 可以保留，帮助读者看到真实回答。仅用于确认导出顺序、批量扫描所有标签或内部一致性的 `stopifnot()`、批量 `for (...) table(...)`、行数/哈希/覆盖核对属于 QA，放到 `# 输出` 之后，不能冒充业务背景。

公开 R 开工前先做四问：

1. 不读笔记其它章节，读者能否从代码开头说出“这份代码在定义什么”？
2. 在第一组 raw 名称出现前，读者是否已经知道这些记录的题目含义和周期结构？
3. 在 helper 或公式出现前，读者是否已经知道输入怎样变成最终结果？
4. 去掉变量名和代码语法后，注释是否仍能独立说明业务逻辑？

任一答案为否，公开 R 尚未达到可发布状态。这里按正向可读性判断，不以注释行数、标题数量或词语命中为通过标准。

## 1.2 R 头部固定模板

正式定义脚本开头固定使用以下风格：

```r
rm(list = ls())

for (pkg in c("devtools", "openxlsx", "dplyr")) {
  if (!requireNamespace(pkg, quietly = TRUE)) {
    install.packages(pkg)
  }
}

library("devtools")
library("openxlsx")
library("dplyr")

install_github("ZhidoHuang/dbCodeBookr") # 提示更新包, 可选3跳过，首次使用时需要安装
library("dbCodeBookr")

dt <- read.csv("raw_data.csv")
name_z <- read.csv("raw_codebook.csv")

data <- dt
data[data == ""] <- NA
```

CHARLS 的导出端固定生成不带 BOM 的 UTF-8 `raw_data.csv` 和 `raw_codebook.csv`；正式公开 R 只使用上面的普通 `read.csv()`。不得在公开代码中追加 `fileEncoding`、`encoding`、`col.names` 或 `check.names = FALSE`，也不得再用 `names(dt)[1] <- "ID"`、`names(name_z)[1] <- "Easy.label"` 事后修补。若不同 File 或模块存在同名 raw，必须在 dbCodeBook 的变量选择阶段按来源身份设置唯一别名，预览确认表头唯一后再下载；正式 R 不得按列位置重命名。编码、普通表头和同名来源问题都必须在 dbCodeBook 导出或恢复工具中解决。

读取区只负责读取数据、统一空字符串和必要的基础类型。`raw_row_count` 等 QA 统计放在 `# 输出` 之后；目标周期筛选若确有必要，放在正式输出的数据边界；家户数据确实缺少 `id` 时，直接陈述并执行确定的派生规则，不写“如果缺少则……”的防御分支；公开代码不得用 `raw_vars <- name_z$newname` 绕行取得数据列。

已经有 `data[data == ""] <- NA` 时，不要再写全局的 `data[data == "null"] <- NA`。普通定义脚本也不要写泛化的 `normalize_text <- function(x) { ... "null" ... }` 作为默认清洗入口。需要清理某个变量时，直接对该具体变量做 `trimws(as.character(...))` 和 `table()`，再按真实取值逐项重编码。

## 2. `recode.chr()`

`recode.chr()` 是 RStudio 代码生成辅助，不是运行时清洗函数。

正确理解：

- 对具体变量读取当前真实非缺失取值。
- 生成一段逐项枚举原值的 `case_when()` 代码。
- 在 RStudio 中会把 `recode.chr(data$var)` 这一行替换成生成代码。
- 只有确实由 `recode.chr(data$var)` 对同一变量生成、再按真实取值修订的转换块，才保留 `# recode.chr(data$var)`。该注释必须紧贴对应赋值，下一条非空代码必须仍是 `data$var <- case_when(...)`，而且判断对象也是 `data$var`。用于预览真实取值的 `table()` 放在该注释之前。
- 跨年份来源合并、多变量计分、汇总、阈值判定、回溯或其它自定义定义逻辑，不是 `recode.chr()` 生成代码，不得在前面添加 `recode.chr()` 注释。

正确写法：

```r
table(data$var, useNA = "ifany")

# recode.chr(data$var)
data$var <- case_when(
  data$var == "原始值1" ~ "标准值1",
  data$var == "原始值2" ~ "标准值2",
  TRUE ~ NA_character_
)

table(data$var, useNA = "ifany")
```

禁止写法：

```r
clean_var <- function(x) {
  # recode.chr(x)
  case_when(
    grepl("some pattern", x) ~ "some value",
    TRUE ~ NA_character_
  )
}
```

规则：

- 必须针对具体变量，例如 `recode.chr(data$raw_var_clean)`，不能写 `recode.chr(x)`。
- 普通分类重编码必须逐项枚举真实原值，使用 `data$var == "原值" ~ "新值"` 精确匹配。
- 不得用 `grepl()`、正则、模糊匹配或 helper 函数伪装成 `recode.chr()` 生成代码。
- 如果确实需要 `grepl()`、年份条件、跨变量条件、回溯逻辑，那是自定义定义逻辑，不能标成 `recode.chr()` 生成代码。

## 3. `recode.num()`

`recode.num()` 同样是 RStudio 代码生成辅助。

适用场景：

- 原始变量是字符或混合编码，需要转成数值。
- 需要把若干非数值标签映射成数值。

要求：

- 只有确实由 `recode.num(data$var)` 对同一变量生成的数值转换块，才保留具体变量注释，例如 `# recode.num(data$var)`；下一条非空代码必须继续赋值给同一个 `data$var`，并以该变量自身的原值为转换对象。
- 固化生成后的重编码代码。
- 正式 Rscript 不依赖 `recode.num()` 的运行期返回值完成转换。
- 只有 YES/NO 二分类默认使用 `1/0`；其它分类变量默认保留英文/ASCII 文字标签。
- 已经由多个来源计算出的得分、合计变量、跨年份统一变量和阈值变量，不需要再伪装成 `recode.num()`；直接陈述并实现其真实计算逻辑。

## 3.1 定义笔记与宣传代码提示的边界

- 定义笔记的公开 R 与正式业务 R 保持一致，不显示 `raw_data.csv` 的网站获取提示。
- `# raw_data.csv从网站dbcodebook.cn对应笔记，go to提取变量获得` 只属于公众号 SVG 与富文本的读者展示层，由宣传公共工具在渲染代码块时注入。
- 不得为了让宣传显示该提示而把它写回正式定义 R；宣传载体也不得把注入后的提示反向同步进定义笔记。

## 4. `yyds_coalesce()`

多个候选来源变量按优先级合并时，优先使用 `yyds_coalesce()`。

使用前必须用块级注释说明：

- 为什么有多个候选来源。
- 各来源对应哪些年份或路由。
- 优先级按什么原则排列。
- 哪些值不是具体分类，需要后续特殊处理。

示例注释（仅展示注释写法）：

```r
# 按周期整理同一概念的多个候选来源。
# 优先使用正式主来源；主来源没有可用记录时，再按已确认顺序使用补充来源。
# 状态标记不等同于最终分类，需要在赋值前按正式逻辑单独处理。
```

## 5. 代码注释规则

代码注释不是解释每一行语法，而是帮助人理解关键定义逻辑。

必须写块级注释的情况：

- 跨年份变量合并。
- 多个来源变量合并。
- 变量同名但跨波次语义漂移。
- 特殊变量假设，例如某个整理变量没有独立标签说明。
- no-change、上一轮回溯、题目衔接或进入题组条件会影响定义结果。
- 会影响用户理解或后续分析选择的数据问题。
- 复杂 helper / 函数承担定义判断，例如按题组计分、处理特殊选项、合并多来源、判定冲突或异常编码。

注释应回答：

- 这一步为什么需要做。
- 解决什么数据问题。
- 对最终变量有什么影响。
- 哪些中间列只用于核对定义结果，不进入正式分析变量。
- 该代码块的输入结构是什么，例如 checkbox、Yes/No、连续数值、上一轮核对题或多来源记录。
- 缺失、特殊选项、冲突或异常编码在这一步如何影响最终变量。

公开 R 代码注释必须按读者实际阅读顺序解释非显然转换。复杂 helper 前至少说明输入结构、为什么需要该 helper、关键缺失/特殊值规则，以及它对最终变量的影响。注释密度按认知难度决定，不按代码行数机械添加；不能只写总标题或维护者视角摘要，让读者从实现反推定义。禁止把内部流程、QA 行话、路由、后台、工具、旧版本史等当作用户解释。

公开 R 代码优先展示定义步骤，不以复用或 DRY 为首要目标。当自定义 helper 需要读者跨函数追踪参数才能理解最终变量时，应改为按年份、来源或题组展开的直线代码。对 2-5 个年份或来源分支，允许少量重复，换取“原始题目 -> 清洗 -> 特殊值 -> 最终变量”的就地可读性。只有真正降低读者认知负担、名称和输入输出一眼可懂的简单 helper 才保留。只用于汇总检查且不进入正式输出的状态列和 helper 放在 `# 输出` 之后。注释不能替代代码结构简化；验收应同时检查注释可读性和实现可读性。

不要写成：

```r
# 创建 data.frame
# 赋值
# 循环
```

应该写成（示例只展示目的注释写法）：

```r
# 按正式优先级合并同一概念的多个来源。
# 主来源没有可用记录时才使用补充来源；状态标记在最终赋值前单独处理。
```

特殊变量假设示例：

```r
# 补充来源只有编码，没有独立文本标签。
# 使用前依据正式 codebook 或明确裁决确认编码含义，并说明它补充哪一类记录。
```

## 6. 笔记写作规则

笔记是给用户看的，不是 QA 报告。

笔记不要写：

- 常规缺失处理，例如“缺失或无法识别设为 NA”。
- “见 QA”“QA 显示”“自检通过”。
- `transaction`、`raw_codebook`、`mapping`、`explicit`、`lookback` 等内部词。
- “不生成 xxx” 这类用户没问的排除项。
- 过细的工程过程，除非会影响变量理解。

笔记应该写：

- 变量是什么。
- 来自哪些年份或题目。
- 分类怎么理解。
- 正式编码是什么，中文含义是什么。
- 重要特殊点，但要翻译成人话。

基础变量和派生归类变量要分开写：

- 基础变量：详细说明原始来源、年份差异、加载变量、特殊取值和必要处理。
- 派生归类变量：不重复原始变量来源，只说明基于哪个基础变量归并、合并为几组、每组对应哪些原始类别。

用户版变量说明的语言风格：易懂但不空泛，保留可追溯信息，但把技术词翻译成人话。

推荐小标题：

- 基础变量使用：`定义`、`定义逻辑`、`注意点`。
- 派生归类变量使用：`定义`、`定义逻辑`、`分类`。

强调样式规则：

- 小标题使用加粗，例如 `**定义：**`、`**定义逻辑：**`、`**注意点：**`、`**分类：**`。在 HTML 中使用 `<strong>`。
- 变量名、列名、变量名前缀、函数名、文件名、R 对象、包名和代码对象使用反引号或 HTML `<code>`，例如 <code>raw_var</code>、<code>defined_var</code>。
- 数据取值、编码值、分类值、问卷原始选项和特殊选项使用下划线并加方括号，不加粗、不用反引号，例如 <u>[1]</u>、<u>[0]</u>、<u>[1 Yes]</u>、<u>[2 No]</u>。
- 该样式规则优先作用于 `Criteria`、笔记解释正文和用户可见说明；detail / fixed-table / 原始频数表中的自然数据值暂不强制改样式，除非该值在解释正文中被单独拿出来说明。
- 用户材料统一使用网站名称 `dbCodeBook`，不使用内部名称 `bookapp`。
- dbCodeBook 目录路径保留真实完整层级，使用斜体，不加粗、不用反引号，例如 `*Core data > Demographic data*`。在 HTML 中使用 `<em>`；不得只保留末级目录或自行翻译目录名称。
- dbCodeBook 目录路径通常放在摘要导读、变量入口或数据来源概览中；默认不要写进单个变量的 `Criteria`。只有目录本身会影响定义边界时，才在 `Criteria` 中简短说明。
- 中文解释和一般概念使用普通文本，不额外加粗；避免普通重点和小标题抢层级。

## 用户自由文本公共规则（唯一内容规则源）

本节是笔记摘要导读、`Criteria` 和公众号 SVG 摘要导读的唯一内容与语言规则源。数据库流程、Skill 和宣传载体只能引用本节；载体文件可以补充其独有的结构与渲染规则，但不得另写一套通用语言规则。

共同写作规则：

- **事实有依据：**数字、编码、阈值、权重、区间、来源、周期和优先级，只能来自正式代码、原始标签或明确用户裁决。依据不足时暂停核对，不根据上下文补全。
- **只写有独立解释价值的信息：**删除一句话后，如果读者对变量含义、赋值、比较或使用边界的理解不变，该句不进入用户文本。
- **忠实于判定口径，不照译代码：**允许合并重复分支、调整叙述顺序、使用公式并直接写转换结果；不复述函数名、中间对象、防御性范围判断和程序语法。
- **普通缺失默认省略：**只说明特殊编码转缺失、条件性缺失、完整性门槛、部分项目缺失导致汇总缺失等会改变解释或分析选择的情况。
- **同一事实只陈述一次：**题义、单位或分类已经自然包含的信息，不换一种方式重复。
- **面向普通读者写：**使用简洁、自然、高信息密度的陈述句，不写流程、验收、制作过程或未解释的方法学术语。
- **语言质量不使用机械指标判断：**禁词命中数、句子重合率、改写率和“旧句复用为零”都不能证明语言合格；机器只核对事实、结构和同步关系。

每句话写入前依次判断：是否有正式依据；是否提供独立解释价值；是否放在正确栏目；能否在不损失事实的前提下更短。前三项任一不满足，就不写入当前文本。

### Criteria 内容规则

`Criteria` 使用 `定义`、`定义逻辑`、`分类`、`注意点` 组织内容，其中 `注意点` 为可选栏目：

- `定义` 只回答变量表示什么，不写年份、来源、处理过程、缺失或研究建议。
- `定义逻辑` 只写真正影响结果的判断、赋值、计算、优先级和特殊缺失。按读者容易理解的“判断依据 → 赋值或计算 → 必要的特殊缺失”组织，不逐句翻译代码。
- `分类` 只列最终编码和类别含义；连续变量默认只写“连续变量”和单位。理论最大值、观察范围和极端值进入 QA，除非范围本身属于正式定义。
- `注意点` 只写不属于代码赋值步骤、但影响追溯、比较或解释的事实，包括来源身份变化、题目增删、某周期未设置、适用对象或项目数量变化、可比性与解释边界。
- 没有符合上述条件的注意事项时，省略整个 `注意点` 标题和内容；不得输出“无”“暂无”“不适用”等占位文字，也不得保留空标题。

具体写作要求：

- 普通单题直接写“题义 + 回答选项 + 赋值”。题义和判定不变、只是跨周期更换 raw 变量名时，统一赋值只写一次，周期与来源放在“定义逻辑”的同一编号项中，不另生成“注意点”。
- 不同周期的正式判定确实不同时才分层描述；补充来源、优先级和回填条件按实际触发顺序说明。
- 以公式为核心的计算型变量，`定义逻辑` 按“最终公式 → 组成项的取值条件 → 原始分档或输入值的换算规则 → 完整性条件与缺失传播”组织。先让读者看到最终怎样计算，再解释公式中的输入如何得到。
- 原始选项必须保持问卷或 raw 中的真实标签，不得用推定的换算边界改写原始选项。换算值若来自题目前提、问卷结构或明确用户裁决，应保留原始标签，并在 `注意点` 中说明换算依据及其解释边界。
- 汇总变量的完整性规则从最终变量角度陈述。变量由多个分项合计、汇总或组合时，应说明计算最终变量需要哪些分项可计算，以及任一分项无法计算时最终变量如何处理。造成单项无法计算的具体条件放在前面的组成项规则中，不用其中某一个上游触发条件代替完整的汇总规则。
- 下游变量只是对正式上游变量重新归类时，只说明分组关系；不重复上游已经完成的原始值清洗。
- 正常数值按题目单位保留时，不复述“其余非负数保留原值”等可由题义和单位自然推出的代码条件。
- 不把 `TRUE ~ NA`、未匹配类别或防御性兜底翻译成用户说明。原始数据存在不知道、拒绝回答、不适用等特殊值且会影响结果时，直接说明这些真实取值。
- `注意点` 是否需要说明演变，由语义和可比性是否实际变化决定，不由变量名是否相同决定。同一变量名前后更换题义，或题义、来源身份、适用对象、项目结构及跨周期可比性发生实际变化时，说明前后周期、实际含义和解释影响；题义和判定不变、只是变量名变化时，不在“注意点”重复来源对应。“同名不同义”可在有助理解时使用，不作为固定标签强制出现。
- 当某周期缺少前期对应来源时，按“缺少什么 → 实际如何赋值 → 该值能表示什么、不能表示什么”说明事实，不使用未解释的方法学术语。
- `定义逻辑` 和 `注意点` 多项内容使用 `① ② ③...`；`分类` 使用短横线。小标题单独一行并加粗，内容使用轻量缩进块，不使用表中表或 `<ul><li>`。
- 该规则必须落实在正式 R 的 `definition_data$Criteria` 生成源头，不得只手工修改生成后的 definition HTML 或笔记。

原始矛盾检查是可选专项，仅在用户明确给出口令 `启用原始矛盾专项检查` 后执行。触发后应说明两组定义变量与原始来源、矛盾方向和数量、矛盾来自原始记录而非定义过程，以及定义变量是否保留或修正该矛盾；可靠的周期、来源组合和数量可使用 `<br>` 分行。一个变量由另一个变量直接派生，或正式代码已经执行来源覆盖、优先级或相互修正时，不机械套用“保留原始矛盾”。

推荐在正式 R 脚本中使用只服务 `Criteria` 的 helper：

```r
criteria_item <- function(x) {
  paste0(
    "<div style='padding-left:1.8em;text-align:left;line-height:1.75;margin:3px 0;font-size:0.92em;'>",
    x,
    "</div>"
  )
}

criteria_value <- function(x) {
  paste0("<u>[", x, "]</u>")
}
```

注意不要写成 `margin-left:1.8em; ... margin:3px 0;`。后面的 `margin` 简写会覆盖前面的 `margin-left`，导致缩进消失。若不用 `padding-left`，必须使用不会互相覆盖的完整四值 `margin` 写法。

多份材料同步规则：

- `CHARLS_xxx_definition.html`、`CHARLS_xxx_笔记.md`、QA 和 R 代码中的用户可见定义说明，必须来自同一套文本片段或同一处生成逻辑；不要手工在多处各改一版。
- 单个变量 `Criteria` 默认不写 dbCodeBook 目录路径；目录路径如果需要出现，优先放在摘要导读或数据来源概览。

- 原始记录矛盾只有在事实和数量已经核实时才进入摘要。写明矛盾方向、代表性来源变量和记录数，使读者能看懂同一受访者的哪两类记录彼此冲突；不把定义变量之间的表面差异误写成原始记录矛盾。
- 提示卡用于帮助读者理解本次定义为什么需要跨来源判断，不展开完整赋值流程。除固定卡片标题外，不再追加其它难易评价。没有已确认的复杂性就省略，不为填满模板制造内容。
- 语言自检只做三项：普通读者能否看懂具体发生了什么；每个代表性例子是否交代了必要的周期、变量和含义；去掉抽象类别标签后，句子是否仍然自然完整。机器只核对事实、结构和同步关系，不检查是否出现“例如”“最后发现”等特定措辞。

反例：

> ① 跨年份变量演变：变量名称发生变化。

正例：

> ① 变量名也会随年份变化。例如，某项信息前期使用 `raw_a`，后期改为 `raw_b`；而 `raw_b` 在更早年份记录的是另一项内容，不能仅凭变量名连接不同年份的记录。

- “必要的含义区别”和数据复杂性按实际情况写。自然段不是 `Criteria` 的压缩版，不展开逐变量赋值、计分、特殊编码和逐年 raw 对应。
- 五列表固定使用 `定义变量`、`含义`、`组成`、`覆盖周期`、`对象` 五个表头；其中“组成”填写正式 mapping 对应的原始变量数。定义变量集合与顺序取自 `analysis_codebook`；原始变量数按完整来源身份去重；“含义”与 `Criteria` 定义及 `analysis_codebook$Label` 核对。
- 覆盖周期和对象从正式 `analysis_db` 逐行生成，不设置批量默认值。目标周期必须由数据库 profile 或本次任务显式声明，不能把“当前文件中实际出现的周期”反推为完整周期；覆盖全部目标周期时才写“全周期”，否则列具体周期。CHARLS 直接写年份，ELSA 使用 `Wave N`。
- 对象按各周期非缺失覆盖率概括：全部覆盖周期均达到 `85%` 时写“全样本”；存在低覆盖周期时按相近覆盖率和周期分组，用整十百分比表达并以 `；<br>` 分行。不写精确人数、精确小数、跨度过大的百分比范围，也不用“有变量信息者”等结果反推对象。
- 摘要可以展示真实的检索入口、相关内容类别和正式选取条数，但不写浏览器点击、下载恢复、逐年 raw 明细、逐条定义逻辑、QA、transaction、验收过程或“见下方”等提示语。正文自然左对齐，不使用 `&emsp;&emsp;` 制造缩进。

### 综合指标关系与文献引用

- 只有正式定义变量存在已经确认的“组成项 → 领域 → 总指标”或同类多层关系时，才在摘要两段正文之后、五列表之前增加关系图；普通单层主题省略。
- 关系图只重排正式节点名称，不改写节点文字，不新增公式、阶段标题或解释。公式和计算细节仍放在 `Criteria` 或定义表格中；用户明确要求在关系图中展示时除外。
- 归属关系采用括号结构表达时不再添加箭头。关系图使用无边框、透明背景的 `div` + CSS Grid/Flex 结构，不使用 HTML `<table>`，避免宿主页面的表格样式产生格子、边框或单元格间距。
- 关系图前后各放置一个独立 `<br>`，使它与上方摘要正文及下方五列表形成可见空行；自然源码空行只用于 Markdown 分块，不能代替可见间距。不得使用空表格行或空容器制造间距。
- 文献引用仅收录确实支持本主题定义结构、构造方法或解释边界的正式来源。放在完整定义表格之后、`## 材料`之前；与上方定义表格空一行，多条引用之间不留空行。
- 正式笔记优先收录官方问卷/代码本/技术文档、原始量表或方法文献、正式指南/共识/制度文件。普通应用论文即使经过同行评议，也只在其直接提供不可替代且可复核的构造证据时收录；不能因为“已经发表”或期刊自称同行评议，就称为权威依据。
- 引用正文必须说清该来源直接支持哪一项题义、题项、公式、计分或解释边界，以及哪些部分仍是本项目的跨期统一或分析选择。只支持“有人这样用过”的文章默认留在过程证据，不进入正式笔记；没有高等级来源时宁可明确写“项目定义”，不以低等级论文包装成文献共识。
- 每条引用独占一行，使用连续编号的 Markdown 引用格式 `> 1、文献内容`、`> 2、文献内容`；引用前后不加 `*`，不写空引用或占位内容。
- 期刊文章统一写为：`> 1、作者. [文章标题](正式链接). 期刊名. 年;卷(期):页码或文章号. doi: DOI. PMID: 编号; PMCID: 编号.`。
- 书籍章节统一写为：`> 1、章节作者. [章节标题](正式链接). In: 编者, editors. 书名. 出版地: 出版社; 年份. Chapter 章节号.`。
- 报告或机构文件统一写为：`> 1、机构或作者. [文件标题](正式链接). 出版地: 发布机构; 年份.`。
- 作者、标题、期刊或书名、年份、卷期及页码或文章号按正式来源核对。DOI、PMID、PMCID 有则保留，没有则省略，不写“无”；链接放在标题上，优先使用期刊官网、DOI、PubMed、正式出版页面或机构官网。优先采用来源页面提供的正式 citation，不自行翻译英文标题，也不为统一形式补造缺失字段。

定义口径的指令层级为：明确用户裁决 > 本共享规则 > 单次任务临时措辞。主题脚本不得硬编码与本规则冲突的摘要或 Criteria 口径。
- `### 1-提取变量` 的 `custom-textbox` 必须包含两部分：`<div class="textbox-content">` 中的 `bookapp显示名=变量名` 列表，以及 `<button class="textbox-button" onclick="goToExtractVariables(this)">Go to 提取变量</button>` 按钮。禁止保留占位符 `请在这里输入文本框内容`。迁移和验收时扫描最终 `*_笔记.md`：按钮出现 1 次，占位符出现 0 次，变量列表非空；如需修正，必须改正式 R 的 `extract_box` / `note_lines` 源头，不得手工只改生成后的 md。
- detail HTML / 笔记中的覆盖热力表 category 是展示分组，不改变正式变量。每个概念组固定先显示 `xx source variables`，再显示 `xx defined variables`；多概念主题按概念结构依次成对排列。正式 R 在 category 赋值后必须设置显式 factor levels，并按 levels 排列后再送入生成器，不能依赖字符排序或当前行序。多概念主题必须按概念把 raw 变量和对应分析变量分入不同 category；不要用一个笼统 category 合并所有变量。正式 R 脚本应使用显式映射，并为未匹配变量设置 `Other / check` 或同等警示 category，同时触发 warning 或写入 QA/过程卡。
- 生成笔记时，detail / 组分概览部分只允许出现一个标准标题：`## 定义的组分概览`。禁止旧过程标题壳 `### 3-详情材料`、`3-详情材料`、作为章节壳的 `详情材料`，也禁止重复 `## 定义的组分概览`。迁移和验收时扫描最终 `*_笔记.md`，旧标题壳为 0、标准标题为 1；如需修正，必须改正式 R 的 `note_lines` / 笔记拼装源头，不得手工只改生成后的 md。
### 其它用户可见文本与同步

- 本规则重点约束笔记摘要导读、`Criteria` 和公众号 SVG 摘要导读。公开 R 另须遵守 1.1.1 的业务背景合同；除此之外不再为代码注释建立词语黑名单或主题专属话术。detail 标签等其它自由文本只要求事实准确、语言自然、与正式成果一致。
- 用户材料只解释数据对象、变量语义、周期逻辑、必要来源差异和研究使用影响；制作来源、工具、版本史、验收状态和过程证据留在 QA 或过程目录。
- QA 可以保存覆盖率、冲突、内部来源和异常细节；笔记只保留普通读者理解变量所必需的事实。
- 摘要 `note_lines`、`definition_data$Criteria`、detail 分组、笔记公开 R 代码和已存在的宣传材料必须按各自生成源核对同步；不得只修改生成后的 HTML、Markdown 或 SVG。
- 用户要求调整语言或强调样式时，先修改正式生成源，再刷新对应正式材料。

## 7. 机器检查与触发验收

以下项目必须由固定检查器和执行任务机器闭环检查，不再交给独立验收重复执行。只有机器证据冲突、研究问题未决、公共核心机制边界不足或用户/大脑明确要求时，才按 `定义成果风险触发验收规则.md` 启动限定范围验收：

- 笔记 R 代码块是否截取到 `# 输出` 之前；`# 输出` 之后的 QA、HTML、笔记拼装、可视化 helper 不进入用户版代码材料。
- `# 输出` 之前是否保留公开给用户看的定义主线和正式输出代码。
- 公开 R 是否使用 `# ----------- 标题 -----------` 形成可提取的主要代码大纲，并按实际代码顺序覆盖环境与包、读取数据、主要定义处理、`变量字典` 和正式输出；是否不存在空标题。
- 第一组主题 raw 清单、helper 或定义代码出现前，是否已经交代研究任务、最终结果和原始记录结构；是否没有用标题、裸变量清单或实现代码冒充背景。
- `stopifnot()`、批量标签扫描和内部一致性检查是否位于 `# 输出` 之后；公开区保留的 `table()` 是否针对具体变量并紧邻其实际重编码。
- 每个 analysis 变量是否都有 `add_mapping()` 调用，且 map 是否实际驱动 codebook 的 `original_vars`、`processed_vars`、`count`；是否不存在直接手填绕过。
- R 头部是否使用固定包检查块、`install_github("ZhidoHuang/dbCodeBookr")` 更新提示和直接 `read.csv("raw_data.csv")`。
- `recode.chr()` 是否逐项枚举真实原值。
- 是否残留泛化 `# recode.chr(x)`。
- 普通分类重编码是否残留 `grepl()` / 正则伪装。
- 多来源合并是否使用或合理解释 `yyds_coalesce()`。
- 长代码块是否有解释定义逻辑的块级注释。
- 笔记中是否出现内部 QA 语言、常规缺失处理或技术黑话。
- 正式分类编码是否符合英文/ASCII 默认规则。
- definition HTML 与用户笔记是否使用同一套定义文本和同一套强调样式；不能出现一处更新、一处残留旧说法。
- 用户可见正文是否把 dbCodeBook 目录路径、变量名/代码对象、数据取值/编码值/分类值/问卷选项分别使用正确样式；不得把 <u>[1 Yes]</u>、<u>[2 No]</u>、<u>[1]</u>、<u>[0]</u> 等取值写成 `<code>`。
- 摘要导读 `覆盖周期` / `对象` 是否逐行显式生成；R 源中不得出现 `period = "全周期"`、`object = "全样本"` 作为 `summary_row()` 或同类 helper 的默认参数。
- 摘要导读 `对象` 是否有覆盖率依据；低于 `85%` 的定义变量不得写成 `全样本`。
- 摘要导读对象是否通过双向检查：所有覆盖周期均 `>= 85%` 时必须为 `全样本`；是否不存在“有题目信息者/有变量信息者/非缺失者”等循环表达。
- 摘要五列表的变量集合、概念分组、正式顺序、原始变量数、覆盖周期和对象是否均与正式 `analysis_codebook`、mapping 和 `analysis_db` 事实对账；人工“含义”是否已与 Criteria 和 Label 核对。
- 全部目标周期均覆盖时是否显示“全周期”；混合覆盖对象是否按高覆盖组优先、低覆盖整十百分比分组并用 `；<br>` 分行；是否未使用“其余覆盖年份/波次”。
- 摘要表前是否恰有两个自然段，且不存在制作/提示话术或 Criteria 计分细节搬运。
- 摘要周期术语是否与正式周期列一致：CHARLS `year` 直接显示年份数字并使用“覆盖年份”，ELSA `wave` 对应 `Wave` / “覆盖波次”。
- 已确认且实际影响定义的跨周期来源身份或题义变化，是否在 Criteria“注意点”中准确说明变化及其解释影响；赋值、计分和汇总规则是否仍位于“定义逻辑”；不存在变化时是否未强行生成相关说明。
- 摘要导读正文及相关 HTML 是否不存在 `&emsp;&emsp;` 首行缩进。
- 摘要导读 `对象` 是否存在宽范围表达；`约 xx%-yy% 样本` 若跨度超过 20 个百分点，或混合 `全样本` 与低覆盖周期，必须分段。
- detail HTML 与笔记覆盖热力表是否都按每个概念的 `source variables` 在前、`defined variables` 在后排列；多概念主题是否按概念结构依次成对显示；是否不存在笼统合并 category；`Other / check` 如出现是否已说明原因或返修。
